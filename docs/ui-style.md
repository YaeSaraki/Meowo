# Meowo UI 绘制规范

所有库存菜单采用 **TabooLib 的库存 UI**：`buildMenu<Chest>` / `buildMenu<PageableChest>` 构建、`set(slot,item)` 放置、`onClick(slot)` 绑定（回调拿到 TabooLib 的 `ClickEvent`，左右键与 Shift 都在里面）、`Player.openMenu(inventory)` 打开；列表页的翻页交给 `PageableChest`（`slots` / `elements` / `onGenerate` / `setPreviousPage` / `setNextPage` / `onPageChange`），不要自己算页码。

禁止依赖 NMS、虚拟库存或 Anvil 标题接口，保持 Paper 新版本兼容——`PageableChest` 用的是公开 Bukkit 库存，没有违反这条；`Anvil` 是版本脆弱的标题接口，仍然不用（预设改名走聊天栏输入）。

**槽位只写在一个地方**：各 context 的 TabooLib 适配器（`TabooPomodoroScreens` / `TabooMenuScreens` / `TabooHomeMenus`）用 `companion object` 常量持有布局，页面内容（物品名字、lore、材质）与槽位分开，放在 `PomodoroIcons` 这类纯内容构件里。这样物品文案可以单测，而槽位由构建菜单的那一处统一定义。

代价要说清楚：**把菜单建在框架 DSL 里，槽位几何就无法在 MockBukkit 下单测**（框架需要真实服务端）。因此测试用 `TestPomodoroScreens` 按**同一份公开常量**镜像布局，保住行为与文案的覆盖；"框架本身翻页是否正确、点击是否触发"只能在真实服务端验收。这是选择 C 时明确接受的取舍。

## 统一外观：水晶柱

一套 **house style** 定义在 `platform` 的 `MenuChrome` 里，menu / home / pomodoro 三处共用同一份几何与配色。玩家认的是形状先于文字：**顶端发光晶体＝可点的功能**，柱身是它立着的地方，深板岩柱脚是地面。颜色只是强化，从不承担唯一语义——每一格都仍写着名字和「左键/右键做什么」。

| 部位 | 材质 | 含义 |
| --- | --- | --- |
| 顶行角落 | 紫水晶块 | 边框起点 |
| 顶行中央 | 紫水晶芽（发光） | 柱殿的「冠」，放本页状态/预览 |
| 左右两列 | 晶体头 + 品红/紫色玻璃柱身 + 深板岩柱脚 | 装饰性立柱，把内容框住 |
| 顶行横梁 | 紫色玻璃板 | 信息梁 |
| **底行基座** | **深板岩** | **导航轨**：石头读作「柱子立在其上的地面」，让门/屏障/箭头成为这一行唯一显眼的东西 |
| 列位内容格 | 灰色玻璃板 | 空座位（列表未用的格子） |

`frame(rows)` 只画**边框与左右两列**，绝不碰内容格；`pillar(headSlot)` 返回某根功能柱的柱身与柱脚，柱头由调用方给。因此：

- **功能页**（番茄钟柱殿、编辑器、确认页）＝七根（或两根）功能柱：柱头在第一内容行，柱身与柱脚自动补齐。
- **列表页**（家园列表、预设长廊）＝同样的框，内容格放数据；空位由页面自己补空座位，不是 chrome 补——因为主菜单要靠「不放」来隐藏一格。

chrome 先铺、页面按钮后盖，所以页面永远拥有自己的槽位。

## 总菜单：心形

总菜单画成**一颗左右对称的心**，而不是「几个功能挤在一行」。四个内容行正好放得下一颗心：

```
col:   0  1  2  3  4  5  6  7  8
row1:  ·  ·  ■  ■  ·  ■  ■  ·  ·     11 12 · 14 15   两瓣的上沿（13 是凹口）
row2:  ·  ■  ▢  ▢  ▢  ▢  ▢  ■  ·     19 … 25         最宽的一行
row3:  ·  ·  ■  ▢  ▢  ▢  ■  ·  ·     29 … 33         往里收一格
row4:  ·  ·  ·  ■  ■  ■  ·  ·  ·     39 40 41        心尖
```

| 槽位 | 角色 |
| --- | --- |
| `11` `12` `14` `15` | 两瓣的上沿（纯装饰，`@none`） |
| `19` … `25` | 最宽的一行：家园 / 番茄钟 / 小晶簇 / 商店 / 钱包，两侧是轮廓 |
| `29` … `33` | 幻翼 / 核心 / 体型，两侧是轮廓 |
| `39` `40` `41` | 心尖（纯装饰，`@none`） |

**为什么必须对称。** 旧版把四个功能放在 `20/22/23/24`——左边空一格、右边挤三格，没有中心，视线找不到落点，玩家扫一眼不知道该先点哪。对称柱殿给了画面一个中心（`13` 的核心）和两条对称的边；换成心形之后这个道理没变，**变的只是形状**：心给了一个中心（`31` 的核心）和三条对称的边，"这是一颗心"这件事在读文字之前就成立了。

**对称轴是第 4 列**（槽位 `13` / `22` / `31` / `40`）。一格的镜像格是 `9 × 行 + (8 − 列)`，所以 `20↔24`、`21↔23`、`30↔32`。**改一格就必须连它的镜像格一起改**，否则心立刻变歪。`MenuChromeOnMainMenuTest` 把「每个画出来的格子都有它的镜像」和「轮廓是一种材质」这两件事钉住——歪掉在截图里很难看出来，在测试里一眼就能看见。

**这个界面不开柱身。** 功能页的柱头会自动长出柱身（`MenuChrome.pillar`），而柱身会从两瓣上沿往下拉，把心切成两半。所以 `ui.yml` 里这一屏写了 `pillars: false`——柱殿是默认样式，要退出它得明说。

**装饰格必须写明自己不可点。** 轮廓、心尖与核心的 lore 都有一句「点了不会发生什么」。理由与 `UIButtons` 那条一致：一个点了没反应的格子如果长得像按钮，玩家点过一次之后就不再相信整个菜单。

> 注意：功能格**不是**彼此的镜像——家园不等于钱包。对称的是外框（轮廓成对），不是内容。把 `20` 和 `24` 做成同一个图标才会真的破坏它：那是把两个不同的功能伪装成一个。

**两格是「内容随玩家变」的。** 幻翼（`30`）的名字跟着开关走，体型（`32`）的 lore 带着当前倍数——这两样配置写不出来，由 `menu` 模块在打开时用 `overrides` 填。配置只负责槽位、图标、动作与静态文案。

## 配置文件版本

`config.yml` 顶部有 `config-version`。它是**整个插件配置**的版本号——管着两份服主可以改的文件：这份 `config.yml`（选项）和 `ui.yml`（菜单布局）。启动时，凡是版本落后的文件，都会被补上 jar 里新增的键，**并带上原注释**。

> **版本号只有这一处。** 插件从 `config.yml` 读出它，代码里没有第二份副本。曾经有过一份
> （`ConfigVersionMerger.CURRENT_VERSION`），而两份副本会互相矛盾——矛盾的那一种恰好最安静：
> 加了键、只改了文件里的数字，于是插件以为每个服主的文件都已经是最新的一版，什么都不补，
> 新键从此谁也没收到，而且**不报任何错**。现在版本号写在文件里，测试里有一条盯着它不许再分叉。

> **改配置的任何一部分都要 +1：选项和布局都算。** 以前版本号只管 `config.yml`，于是插件加了菜单
> 按钮、版本号不动，服主的 `ui.yml` 也就永远不会被补——而布局是「服主那份整个说了算」，新按钮
> 就那么不见了，日志里一个字都没有。一个版本号既然叫全局的，就得真的全局。

规则只有一条：**只补没有的，已有的一律不动。**

- 服主改过的值不会被覆盖——版本升级绝不能顺手重置别人的调参。
- 键不存在才写；已存在的键**不读、不比、不改**。
- 文件版本**高于**当前代码时完全不碰（降级服务器不该被改写）。
- 已经是当前版本就一个字节都不写：服主故意删掉某行回到默认值，不该在下次启动又被补回来。

**形状不同的键会被跳过并警告。** 服主在 `teleport` 写了一个字符串，而新版那里变成了一个区块——递归下去就得用 `createSection` 盖掉他的值。保留他的值、放弃补子键、并打一条 `WARNING` 列出这个路径，比静默覆盖好。

> ⚠️ **删除的键不会自动清理。** 一个被移除的选项值得一行日志和一句更新说明，插件不该偷偷从别人的配置文件里删行——那个文件里还有 API key 和价格表。

**所有页面一律六行 Chest**：**内容固定在第 1–4 行的第 1–7 列**（槽位 `10..43`，一个列表页 28 格），底部操作区固定 `45` 上一页、`49` 主操作、`50` 返回上级、`53` 下一页或关闭。确认页也做六行，空格用空座位铺满——「三行确认页的第二行」这种按页而异的导航几何，正是最难找出口的东西。翻页后重新读取当前服务状态，页码始终限制在有效范围。

**每个页面都必须有「关闭」**，位于 `53`；有上级的页面还要有 `50` 返回。两者都是具名＋有 lore 的独立材质（门 / 屏障 / 箭头），**不得**使用构成边框的玻璃板：玩家找出口时看到的会是一排没有 tooltip 的紫色玻璃，分不清哪个能点。

**任何页面都不得引用超出自身行数的槽位**——那不是排版问题，而是把一个不存在的格子交给适配器。`PomodoroIntegrationTest` 有两条不变量测试盯这个：越界槽位，以及**装饰不得覆盖功能格**（确认页的空座位曾把两根功能柱盖掉，界面看起来正常却点不动）。

## 色彩与信息

标题用浅色，说明用灰色。水晶柱头只有「这一格有功能」的意思，不表示「重要程度」。三处读数（BossBar / 屏幕标题 / 头顶文字）用同一套字形：`◆` 起头、`┃` 分隔，与菜单同一套语言。

左键执行主要动作，右键打开设置或另一条路径（内置预设右键＝复制再改），Shift+左键才是破坏性动作（删除），且**必须**先过确认页。每一格的 lore 都要写出这三者中真正生效的那几条，未生效的不写。收费操作先打开确认页，显示实际币种与费用；不得把固定价格写死为最终扣款承诺。

**不可用 ≠ 变灰**：一格里做不到的事（例如会话没在跑时的「暂停」）不画成灰色按钮再拒绝，而是在 lore 里把当前状态说清楚。灰色按钮仍然长得像按钮，点下去还得解释为什么没反应。

**页面必须能原地重绘。** 任何改变「本页显示内容」的操作（开关读数、阶段切换）都要重画**已经打开**的页面，而不是等玩家关掉再打开。`PomodoroScreens.refresh` 只替换物品、不重建菜单，因此 TabooLib 已绑定的点击处理器仍然有效。只重绘**展示状态**的那一页（番茄钟柱殿）；列表页与编辑页重绘会丢掉正在输入的内容。

## 屏幕标题的刷新节奏

屏幕标题**每秒重发一次，且一直显示**。这里曾经用错过一个前提，结论记下来：

Adventure 在 stay 到期的**那一刻**就把标题清掉。旧实现为了「避免闪烁」把重发间隔设成和 stay 相等（`pomodoro.title-refresh-seconds`，默认 5 秒），结果每一轮都恰好在 stay 结束的那一帧出现空档——读数于是每几秒闪一次，正是最初要修的那个毛病。**stay 不该拿来当更新间隔。**

正确做法是两个值解耦：

- **重发：每 tick 一次**，倒计时和时钟永远一致，读数稳定停在屏幕上。
- **stay：只要够长就行**（同一个 `title-refresh-seconds`，默认 5 秒），作用是兜住一次掉 tick 或卡顿，不让标题在两次刷新之间提前消失。

**淡入淡出必须为 0。** 这正是「每秒重发」不会变成闪烁的原因：零淡入时重发是**替换**而非**重播淡入**。反过来说，如果哪天淡入淡出被改回非 0，每秒重发就会变成闪烁——这两件事是同一个决定的两面。

## 生命周期与权限

锁定点击、拖动与手持物，验证点击者是页面所有者。库存点击后的换页与业务调用延迟至下一 tick。关闭或模块卸载时释放页面资源；异步结果必须回主线程并检查模块仍运行。

menu 模块负责总菜单及 homes 总览；home 模块负责详情、收费、存储和传送。通过 api 的 HomeMenuAPI/MenuAPI 交互，不跨 context 导入实现类。每次打开页面和执行业务都重新检查权限。

## 导航

新家默认开启原版定位条标记并使用 bowtie 蝴蝶结。BossBar 显示相对视角的方向刻度，中央竖线表示正前方，菱形表示目标，附带距离和高度差。`/home nav off`、总览的关闭导航按钮和详情的再次选择都可关闭；隐藏目标、退出或模块关闭时移除 BossBar。传送完成不自动开启辅助导航。
