# 08 · 坑与反模式

按**症状**检索。每条格式：现象 → 根因 → 修法。

## 1. ⚠️ 测试报 `NoClassDefFoundError ... (wrong name: ...)`，但测试本身全绿

**这是本项目最可能咬人的坑。**

### 现象

构建失败在 `:shared:test`，报告里所有测试都 pass，却多出一个「失败」的测试：

```
> Task :shared:test FAILED
Could not execute test class 'com.meowo.shared.ContextManagerTest 2'.
Caused by: java.lang.NoClassDefFoundError: com/meowo/shared/ContextManagerTest 2
           (wrong name: com/meowo/shared/ContextManagerTest)
```

同时 `shared/build/test-results/test/` 里 `ContextManagerTest.xml` 显示 `failures="0"`。

### 根因

**iCloud Drive 的「冲突副本」。** 项目位于 `~/Library/Mobile Documents/com~apple~CloudDocs/`，
当同一文件被两个进程/机器同时写入，iCloud 不会覆盖，而是生成 `Xxx 2.ext` 副本。

`build/` 目录里因此残留了一批 `Xxx 2.class`，它们与正本**字节完全相同**
（`cmp` 验证一致），但缺少 iCloud 扩展属性（`ls -l` 显示没有 `@`）：

```
-rw-------  4941  ContextManagerTest 2.class     ← iCloud 冲突副本
-rw-r--r--@ 4941  ContextManagerTest.class        ← 真正本
```

Gradle 的测试类扫描按**文件名**推导类名，于是去找 `com.meowo.shared.ContextManagerTest 2`
——这个类名不存在（`.class` 内部的真实名字是 `ContextManagerTest`），加载失败。

本机实测：一次污染会产生 **50 个**这样的重复 `.class`，散布在
`shared/`、`api/`、`platform/`、`core/`、`contexts/*/` 的 build 输出里。

### 修法

```bash
./gradlew clean
find . -name "* 2.class" 2>/dev/null | wc -l    # 应为 0
./gradlew test :core:build verifyArchitecture verifyCoverage --no-daemon
```

`clean` 之后 `find` 返回 0，重新构建 `BUILD SUCCESSFUL`。

### ⚠️ 但 `clean` 清不掉整目录的冲突副本（2026-10-08 实测）

iCloud 不只复制文件，也会复制**整个 build 目录**：`contexts/meowo-hat/build 2/`、
`build 3/`、`contexts/build 2/`、`shared/build 2/`。`./gradlew clean` 只删它自己知道的那个
`build/`，这些**以目录形式存在的副本会原样留下**，里面还带着 `HatContext 2.class`
这类冲突文件。

那时症状会变成另一种、更难看出来的样子——**`clean` 之后依然大面积失败**，而且报的是
测试自己的 lambda 类找不到：

```
java.lang.NoClassDefFoundError: com/meowo/core/PrivateChannelFilterTest$setUp$3
  at com.meowo.core.PrivateChannelFilterTest.setUp(PrivateChannelFilterTest.kt:69)
Caused by: java.lang.ClassNotFoundException: ...$setUp$3
```

同一次运行里 `core` 的 199 项测试大面积红，而 `PrivateChannelFilterTest$setUp$3.class`
在 `build/classes/` 里**明明存在**（`ls` 能看到）。看到"类存在却 ClassNotFound"、
且失败集中在少数几个测试类时，先怀疑这个。

修法（`clean` 之外还要扫目录与带序号的文件）：

```bash
./gradlew clean
find . -maxdepth 3 -name "build [0-9]*" -type d      # 整目录副本，clean 不管
find . -name "* [0-9].class" -o -name "* [0-9].jar"  # 带序号的文件副本
```

确认它们只是副本（里面的名字都带序号）后移走或删除。整目录副本可以临时改名保留，
确认无影响再删——**不要**在没确认的情况下直接 `rm -rf` 一个看起来像 `build 2` 的路径。

### 预防

- **每次完整验证前先 `./gradlew clean`。**
- `clean` 之后**再扫一次**上面两条 `find`：只信 `clean` 是这次踩坑的原因。
- 把 `build/`、`contexts/*/build/` 保持在 iCloud 的「不优化」名单里更好——
  但本项目没有 `.gitignore` 之外的 iCloud 排除配置，最省事的就是养成 `clean` + 扫描的习惯。
- 怀疑时先 `find . -name "* 2.class"`：非 0 就是这个问题，**不要**去 debug 测试代码。

## 2. 玩家看到原始键名（如 `error-my_new_error`）

**现象**：新增 `EconomyError` 枚举值后，玩家收到 `error-my_new_error` 这样的字面串，没有报错。

**根因**：`Messages.text()` 找不到键时**返回键本身**（`platform/.../Messages.kt`）：

```kotlin
fun text(key: String, vararg args: Any): String {
    var result = values[key] ?: key      // ← 静默回落
    ...
}
```

而 `PlatformHost.reply` 拼的是 `"error-${code.name.lowercase()}"`。

**修法**：在 `lang/zh_CN.yml` **和** `lang/en_US.yml` 都加 `error-my_new_error`。
见 [05 §5](05-改造手册.md)。

对账命令：

```bash
grep -o 'error-[a-z_]*' core/src/main/resources/lang/*.yml | sort -u
```

## 3. 新 context 没打进 jar / 运行期 `NoClassDefFoundError`

**根因**：`core/build.gradle.kts` 有**两处**独立清单，漏一处症状不同：

| 漏哪处 | 症状 |
|---|---|
| 漏 `taboo"(project(...))`（第 14-20 行） | 编译通过，**运行期** `NoClassDefFoundError` |
| 漏 `evaluationDependsOn`（第 4 行） | TabooLib 打 jar 时报找不到项目 |

**修法**：两处都加。见 [05 §1 ④](05-改造手册.md)。

## 4. reload 后模块没生效，或 `reload-partial` 误报

**根因**：`MeowoRuntime.applySettings` 的**启用顺序是硬编码的**，
`teleport` 依赖 `economy` 的服务注册。

- 新 context 插在 `teleport` 之前 → 拿不到 `SettlementAPI` → `requireNotNull` 抛异常。
- reload 成功判定（`MeowoRuntime.kt:45`）用了一个硬编码表达式，
  新的依赖关系**没有**被反映进去 → 误报 `reload-partial`。

**修法**：新 context 放最后启用；并检查那句 `expected` 表达式是否需要剔除新依赖。
见 [05 §1 ⑥](05-改造手册.md)。

**排障入口**：`/meowo info` 显示的是**实际启用状态**（`contexts.ids()`），
不是配置期望值。永远以它为准。

## 5. 关停时玩家余额丢失 / 传送费没退

**根因**：破坏了关闭顺序。`ContextManager.close()` 是**逆序**关闭，
依赖启用顺序：`economy → menu → render → teleport → spawn`
⇒ 关闭 `spawn → teleport → render → menu → economy`。

若 economy 先关连接，teleport 随后排队的退款任务就会在**已关闭的 JDBC 连接**上执行。

**修法**：不要在 `ContextManager` 里加「按 id 排序」之类看似合理的逻辑。
顺序是**退款能落地的前提**。见 [02 §3](02-运行时与生命周期.md)。

同时不要在任务执行中强行 `close()` 连接——`EconomyApplicationService` 用
`terminated()` 回调在真正排空后才关库，超时也只是记失败，不中断。

## 6. ⚠️ 架构门禁「漏检」新模块

**现象**：新 context 里 `import com.meowo.economy.*`，`verifyArchitecture` 却通过。

**根因**：`build.gradle.kts` 里的 `pure` 和 `contexts` 两个列表是**硬编码的**。

新模块不在列表里就**完全不被扫描**。而且跨 context 检查只扫
`contexts/meowo-X/src/main`，**不扫** `contexts/meowo-X/domain/src/main`
—— 所以纯领域模块除了加进 `pure`，还要确认它在列表里。

**修法**：新增模块后手动加进 `build.gradle.kts` 的这两个列表，然后
**临时插一个违规 import，确认门禁真的会失败**：

```bash
printf 'import net.kyori.adventure.text.Component\n\npackage com.meowo.X.domain\n\nval p = Component.empty()\n' \
  > contexts/meowo-X/domain/src/main/kotlin/…/Probe.kt
./gradlew verifyArchitecture   # 必须失败，并点名是哪个包名
```

绿了就当通过是这一节最常见的误读：**门禁跑过 ≠ 门禁在扫你**。

### 这条清单自己的失败方式

`05-改造手册` §1⑧ 和本节曾经都**抄了一份列表**，并写着「现有 5 个 context」逐个列出。
真实值早已是 13 个，而且 `pure` 从 3 个长到 5 个。
文档里复写一份列表，就等于给了它一条**独立于唯一来源的漂移路径**——
两份都自称权威，读的人只会看到过时的那份。

**要抄的东西不能有两份。** 文档应该指向 `build.gradle.kts` 并说清行号，
而不是把内容再写一遍。

注意：编译期另有一层保护（context 之间无 `project` 依赖，直接 import 编译不过），
但**如果有人同时加了 Gradle 依赖**，就只剩 `verifyArchitecture` 兜底了。

## 6b. ⚠️ 新 context 的发言者归属错（真实发生过）

**现象**：加完 `spawn` context 后，`/spawn` 的全部提示都由 `<MeowCat>` 发出，
而不是设计中的 spawn 猫；管理员改 `lang/*.yml` 的 `speaker-spawn` 键**毫无效果**。

**根因**：`Messages` 的归属解析是**白名单式的**（见 [05 §4](05-改造手册.md)）：

```kotlin
private fun speakerOf(key: String) = when {
    SPEAKER_KEYS.containsKey(key) -> SPEAKER_KEYS.getValue(key)        // 精确键
    else -> SPEAKER_PREFIXES.firstOrNull { key.startsWith(it.first) }   // 前缀
        ?.second ?: "system"                                          // 兜底 = 系统猫
}
```

`SPEAKER_PREFIXES` 里没有 `spawn-`，于是所有 `spawn-*` 落到兜底的 `system`。
**这不是崩溃，是静默降级**——所以构建全绿、覆盖率正常，只是署名错了。

**连带影响**：`speaker-spawn` 成为**死配置**。`Messages.speaker` 读的是
`DEFAULT_SPEAKERS[id]`，而 `speakerOf` 根本没返回过 `"spawn"` 这个 id，
所以语言文件里那行永远不会被查询。

**修法**（两处都要，缺一仍会错）：

```kotlin
val DEFAULT_SPEAKERS = mapOf(..., "spawn" to "WarpCat", ...)   // id → 默认名
val SPEAKER_PREFIXES = listOf(..., "spawn-" to "spawn", ...)    // 键前缀 → id
```

**为什么测试当时没抓到**：`MeowoRuntimeTest` 里的 `ownerOf` 是**手写镜像**
`SPEAKER_PREFIXES` 的独立实现，它自己也漏了 `spawn-`，于是两边一致地错，
断言照样通过。**镜像实现必须和被镜像的代码一起改**，否则它测的是自己的错误理解。

现在测试已加两条锁定：逐 id 断言 `speaker("spawn") == "WarpCat"`，
以及对 `spawn-warmup` / `render-spawned` / `tpa-incoming` 等键断言归属到各自的猫，
并断言所有发言者**恰好 7 字符**（4 + `Cat`），防止将来又出现宽度不齐。

**自查**：新增 context 后，在测试的 `ownerOf` 镜像里也加一行。
两处对不上，早晚会分叉。

## 6c. ⚠️ 客户端语言匹配不到语言包（per-player 切换的静默失效）

**现象**：实现了按客户端语言切换，英文玩家的客户端明明是英文，
收到的却还是中文；**不报错、不崩溃、测试也可能是绿的**。

**根因**：`Locale.ENGLISH.toLanguageTag()` 返回的是 **`"en"`**，不带地区码。
只做精确匹配就永远匹配不到 `en_US`：

```kotlin
// ❌ Locale.ENGLISH → "en"，永远 ≠ "en_US"
bundles.keys.firstOrNull { it.equals(code, ignoreCase = true) }
// ✅ 先精确，再退回「只比语言码」
bundles.keys.firstOrNull { it.equals(code, ignoreCase = true) }
    ?: bundles.keys.firstOrNull { it.substringBefore('_').equals(code, ignoreCase = true) }
```

`Locale.US` → `"en-US"` → 归一化后是 `"en_us"`，**能**匹配；
但 `Locale.ENGLISH` → `"en"` 就不行。两种写法只差一个地区码。

**为什么难发现**：`player.setLocale(Locale.ENGLISH)` 是测试里最自然的写法，
而真实客户端的 `en_us` 恰好能匹配——所以**只在用无地区码 Locale 的测试里暴露**。
这个 bug 是被 `each player reads messages in their own client language` 抓出来的。

**修法**：见上。另外给未知语言留回落（`fr` → `defaultLocale`），
别让玩家看到空文案。

**同类提醒**：`Player` 同时有 `locale(): Locale` 和 `getLocale(): String`，
Kotlin 会为后者**合成一个同名属性并遮蔽前者**，
写 `player.locale.toLanguageTag()` 编译不过，必须写 `player.locale()`。

完整机制见 [11 · 多语言与 per-player 切换](11-多语言与per-player切换.md)。

## 6d. ⚠️ 跨版本 API 漂移：教程在 26.2 编译不过

**现象**：照着 1.21 时代的骑乘教程写 `player.startRiding(mob)`，
编译报 `Unresolved reference: startRiding`。而那段代码**语法完全正确、思路完全正确**。

**根因**：`startRiding` / `stopRiding` 在 Paper 26.2 **已被移除**。
现在只有 `addPassenger` / `removePassenger` / `eject` / `leaveVehicle`。

**怎么确认（别猜）**：

```bash
A=$(find ~/.gradle/caches -name "paper-api-*.jar" | grep -v sources | head -1)
D=$(mktemp -d); cd "$D" && unzip -q -o "$A" "org/bukkit/entity/Entity.class"
javap -p org/bukkit/entity/Entity.class | grep -iE "riding|passenger|vehicle"
```

**为什么它特别阴险**：它不是「写错了」，而是「**曾经是对的**」。
网上绝大多数教程、包括 LLM 生成��代码，默认都停在 1.21 时代。
这正是红线 [01 §9](01-架构红线.md) 要写「以 `docs/versions.md` 为准，不要照抄 plan.md」的延伸——
**plan.md 里的示例 API 同样可能已经过期**。

**做法**：任何**调用 Bukkit/Paper API** 的新功能，动笔前先 `javap` 一次。
一行命令，比写完再 debug 快一个数量级。
本项目已踩过的同族坑还有：`PlayerCooldownEvent` 在 26.2 不存在（见 [10 §2](10-spawn调研.md)）。

**弃用 ≠ 删除，而且编译器不拦**：`org.bukkit.event.entity.EntityKnockbackEvent` 在 26.2 里
还在、照常编译、照常有监听器，只是标了 `@Deprecated(forRemoval = true)`。代价是**启动日志**
里对每个注册在它上面的监听器刷一条 "Server performance will be affected"。

替代品就写在弃用注解的 `@deprecated use ...` 里（Paper 换成了
`io.papermc.paper.event.entity.EntityKnockbackEvent`），而两个类**同名并存**，
`javap` 的类列表不提示谁是替代品——得翻 sources jar。
**编译不报错、测试全绿、只有真机启动才看得见**：这类问题单测永远抓不到。

**方向别搞反**：`X.addPassenger(Y)` 是「**Y 骑在 X 上**」，
所以让玩家坐上盔甲架是 `stand.addPassenger(player)`，不是反过来。

## 6c. ⚠️ Paper 26.2 移除了 `startRiding`，`getEquipmentSlot()` 在 MockBukkit 返回 null

写 sit / ride / hat 这类"实体与装备"功能时踩到的两个 26.2 变化，都属于**照抄 1.21 教程必踩**。

### `Entity#startRiding` / `stopRiding` 已不存在

逐类核实 `Entity`、`LivingEntity`、`Player`：**全部 0 命中**。26.2 的骑乘 API 是

| 想做的事 | 26.2 写法 |
|---|---|
| A 骑上 B | `B.addPassenger(A)` —— **注意方向，被骑者才是 vehicle** |
| A 下坐骑 | `A.leaveVehicle()` 或 `B.removePassenger(A)` |
| 踢下全部乘客 | `B.eject()` |

`VehicleEnterEvent` / `EntityMountEvent` 等事件都还在，只有这两个便捷方法没了。

### `Material.getEquipmentSlot()` 在 MockBukkit 恒返回 null

这个更阴险：**它不抛异常，直接返回 null**。用 `== EquipmentSlot.HEAD` 判断"这是不是头盔"，
在 MockBukkit 里对**任何**物品都是 false，于是测试会「通过」，而帽子功能在真服上
可能正常、在测试里却永远判不出头盔——覆盖率还是绿的。

**修法**：用纯枚举方法判断，本项目已有先例（见 [10](10-spawn调研.md) 用
`Material.isSolid()` 绕开 `Block.isPassable()`）：

```kotlin
private fun isHelmet(type: Material): Boolean = type.name.endsWith("_HELMET")
```

`org.bukkit.material.ArmorMaterial#getHelmetMaterial()` 是 1.21 之前的经典写法，
**26.2 里这个类已经整个消失**。

### 方块判定该用 Tag

`Tag.BLOCKS_SLABS` 也改名了，26.2 里是 `Tag.SLABS` / `Tag.STAIRS` / `Tag.WOOL_CARPETS`。
这些在 MockBukkit 里是**真实可用**的（已实测 `Tag.SLABS.isTagged(OAK_SLAB) == true`），
比按名字猜后缀更能覆盖模组方块。

**但** ### 继承来的方法，`javap` 不加 `-p` 就看不见

`Stairs` **有** `getFacing()` 和 `getHalf()`，但它们不在 `Stairs` 自己身上，而是继承自
`Directional` / `Bisected`：

```
public interface Stairs extends Bisected, Directional, Waterlogged
public interface Directional { BlockFace getFacing(); ... }
public interface Bisected    { Half getHalf(); ... }
```

只对 `Stairs.class` 跑 `grep getHalf` 会**什么都搜不到**，很容易误判成「API 没了」而放弃用朝向。
本项目就踩过这个坑：一开始按「`getHalf()` 不存在」写了文档，后来为了实现「按楼梯朝向落座」
去核实，才发现方法一直都在。

**正确做法**：用 `-p` 看全部成员，并**顺着 `extends` 追到父接口**：

```bash
javap -p 'org/bukkit/block/data/type/Stairs.class' | head -3   # 先看 extends 了谁
javap -p 'org/bukkit/block/data/Directional.class'
```

同样地，26.2 **没有通用的 `Carpet` 数据类**（只有 `MossyCarpet`，带 `Height: NONE/LOW/TALL`），
所以地毯的精确高度仍然拿不到——这才是「每类方块一个可配置偏移」这一做法真正的原因。

### 楼梯的 `facing` 是「整格面」，台阶在反方向

要按台阶落座就必须知道这一点（Minecraft Wiki 原文）：
`facing` = *the direction the stairs' **full-block side** faces*，而放置时
*「a stair orients itself with the half-block side closest to the player」*。

所以**台阶在 `facing.getOppositeFace()`**。玩家的朝向通常和台阶方向**相反**
（玩家站在台阶一侧往方块看），因此落座偏移**必须以楼梯朝向为准，不能用玩家朝向**。

> 判断新 API 能不能用，两个动作缺一不可：
> ① 在 jar 里 `javap` 确认方法**存在**；② 在 MockBukkit 里**真的调用一次**并断言结果。
> 只做 ① 会被「返回 null 不抛异常」骗过。

## 6e. ⚠️ `getSlot()` ≠ `getRawSlot()`：玩家背包里头部是 5 还是 39？

**现象**：想实现「把任意物品戴到头上」，监听 `InventoryClickEvent`，
判断 `event.slot == 5`，结果**点头部永远没反应**。没有编译错误、没有异常、
没有日志，只有玩家一句「用不了」。

**根因**：一个 `InventoryView` 连接**两个**物品栏，两套下标。官方 javadoc：

> `getSlot()`：可直接传给 `Inventory.getItem(int)`。
> **一个视图连接两个物品栏，所以可能有两个槽共用同一个号码。**
> `getRawSlot()`：可直接传给 `InventoryView.getItem(int)`，**在视图内唯一**。

玩家背包视图（按 E 打开）里，头部是：

| 位置 | 头部下标 |
|---|---|
| 视图内（`getRawSlot` / `InventoryView`） | **5** |
| `PlayerInventory` 内（`getSlot`） | **39**（护甲占 36–39） |

写 `event.slot != 5` 就是在拿 `PlayerInventory` 的 5 号位（一个普通背包格）
去比头部，**永远不等**。

**修法**：判头部一律用 `event.rawSlot`（点击）或 `event.rawSlots`（拖拽）：

```kotlin
if (event.rawSlot != HEAD_SLOT) return
```

`InventoryDragEvent` 同理用 `getRawSlots()`，本版本**没有** `getNewSlots()`。

**为什么它格外难查**：这类 bug 不崩溃、不刷警告、覆盖率报告一片绿——
和 [08 §2](08-坑与反模式.md) 的「静默降级」是同一类。
两个下标都能编译、都能比较，只有玩家真点下去才知道对不对。
**所以这类交互逻辑必须真服 + 真客户端验收**，见 [13 §4](13-hat.md)。

**顺带一条**：`InventoryClickEvent.setCursor` 自 1.5.2 起标注 `@Deprecated`，
官方说明它「会在物品栏计算之前改动玩家手上的物品，容易造成玩家与服务端状态不一致」。
需要把物品退回光标时，改用 `player.inventory.addItem(...)` 更稳。

## 6f. ⚠️⚠️ 取消库存事件后光标没被消耗 → 刷物品

**现象**：`/hat` 上线后，**把一摞物品拖到头上，每拖一次物品数量就翻倍**。
物品复制，无限刷。**本项目真实发生过，且是上一轮「修 bug」时引入的。**

**根因**：取消 `InventoryClickEvent` / `InventoryDragEvent` 只会让**槽位**回滚，
**光标（cursor）上的物品原封不动地留着**。于是：

```kotlin
event.isCancelled = true
if (incoming.amount > 1) give(player, incoming.clone().apply { amount = incoming.amount - 1 })  // 余量进背包
setHelmet(player, incoming.clone().apply { amount = 1 })                                        // 1 个上头
// ← 光标上仍然是完整的 64 个！
```

玩家拿到 63（背包）+ 1（头）+ 64（还在光标上）= **128**。每次重复都会翻倍。

**修法：余量必须回到光标上，而不是进背包。**

```kotlin
val split = HatPolicy.splitForHead(incoming.amount)     // 1 上头，其余留光标
event.setCursor(if (split.cursor > 0) incoming.clone().apply { amount = split.cursor } else null)
setHelmet(player, incoming.clone().apply { amount = split.head })
if (outgoing != null) give(player, outgoing)             // 换下来的旧头饰才进背包
```

**触发它的错误推理**：`setCursor` 官方标注了 `@Deprecated`（说明是「会在物品栏计算
之前改动玩家手上的物品」），于是有人（包括我）认定「不该用 `setCursor`」，
改用 `addItem` 塞进背包——**恰好是复制物品的做法**。

> **教训**：`@Deprecated` 不等于「在这个场景不能用」。
> 取消事件时，`setCursor` 正是**唯一**能正确回写光标的手段。
> 判断一个 API 该不该用，要看**语义是否正确**，不能只看废弃标注。

**防御**：把守恒关系做成纯函数并测死，`HatPolicyTest` 里
`putting one item on the head never duplicates the stack` 对 0..64 全量断言
`head + cursor == amount`。以后任何人再改成分配给背包，这条立刻红。

> 这类「事件取消 + 手动补物品」的逻辑**天然难测**（见 `13-hat.md` 的 MockBukkit 限制），
> 所以**必须**把守恒/分配规则抽成纯函数单测，事件层只做接线。

## 6g. ⚠️ `setCustomName` 对玩家完全无效

**现象**：给玩家设置头顶名牌（`player.customName(...)` +
`player.isCustomNameVisible = true`），**什么都没发生**。没有异常、没有日志、测试全绿。

**根因**：官方 Spigot API javadoc 对这两个访问器写了同一句话：

> `Entity#setCustomNameVisible` / `isCustomNameVisible`：
> **"This value has no effect on players, they will always display their name."**

`setCustomName` 同理。**这些 API 对 mob 完全正常**，所以绝大多数教程
（包括 LLM 生成的）会拿它当玩家名牌的正确做法——在玩家身上就是静默无效。

**修法**：用**计分板队伍的前缀/后缀**，它由客户端渲染在头顶名牌和 Tab 里，对玩家有效：

```kotlin
val team = scoreboard.getTeam("mw_afk") ?: scoreboard.registerNewTeam("mw_afk")
team.suffix(Component.text(" •", TextColor.fromHexString("C9A063")))
team.addEntry(player.name)      // 状态翻转时先 removeEntry 再 addEntry
```

**三个必须知道的代价**：

1. **一个玩家只能属于一个队伍** —— 本 context 拥有它注册的两个队伍（`mw_` 前缀），
   `close()` 必须 `unregister()`，否则 reload 会累积队伍。
2. **后缀也会出现在 Tab 列表和原版聊天里** —— 机制固有，纯 Bukkit 无法只影响头顶。
3. **潜行隐藏名牌归原版管** —— 别再写 `PlayerToggleSneakEvent` 去"跟随"，
   队伍后缀不受插件控制，留着只是假装能控制。

完整实现见 [14 · AFK 与状态圆点](14-afk与状态显示.md)。

> 和 [08 §6e](#6e-) 一样：**编译通过、调用合法、只是什么都不发生**。
> 这类"静默无效"必须靠**读官方 javadoc 的那句话**发现，而不是靠试。
> 判据很简单：**javadoc 里写了 "no effect on X" 的 API，就别用在 X 上。**

## 6h. ⚠️ `TextColor.fromHexString` 只认 `#`，`0x` 前缀返回 null

**现象**：名牌上的状态标记能画出来，但**永远是默认白色，不随状态变色**。
没有异常、没有日志，**测试也全绿**。

**根因**：代码把颜色拼成 NBT 风格的 `0x` 前缀：

```kotlin
val colour: String get() = "0x$rgb"        // "0xC9A063"
TextColor.fromHexString(colour)             // null
Component.text(text, null)                  // null 颜色 = 客户端默认色
```

实测 Adventure 的十六进制词法器：

| 传入 | 结果 |
|---|---|
| `"0xC9A063"` | **`null`** |
| `"C9A063"` | **`null`** |
| `"#C9A063"` | `#C9A063` |

**`0x` 是 NBT 的写法，不是 Adventure 的。** 返回 `null` 不抛异常，
`Component.text(text, null)` 就安静地退回默认色——和 §6g 是同一类静默失效。

**修法**：自己解析，且**对坏值大声失败**：

```kotlin
fun colour(): TextColor {
    val value = rgb.toIntOrNull(16)
        ?: throw IllegalArgumentException("Marker colour must be hex digits, got '$rgb'")
    return TextColor.color(value)
}
```

**原测试为什么是绿的**：它断言的是**中间那个字符串**——
`assertEquals("0xC9A063", MarkerStyle.AWAY.colour)`。
字符串完全正确，而颜色是 null。**断言断在了错误的层。**

> **教训**：颜色/格式相关的断言要断言**最终解析出的值**
> （`.colour().value()`），不是断言拼接出来的字符串。
> 字符串对了不代表下游解析成功。

完整实现见 [14 · AFK 与状态圆点](14-afk与状态显示.md) §2b。

## 7. 事件订阅者不触发

**根因**：`EventBus` 用**精确类型匹配**：`entry.type == event.javaClass`。

```kotlin
if (entry.active && entry.type == event.javaClass) { ... }
```

发子类不会投递给父类订阅者；发父类不会投递给子类订阅者。

**修法**：订阅时传的 `Class` 必须与**实际发布的类**完全一致。
不要设计继承层次来"泛化订阅"。

## 8. `CompletionException` 让业务错误变成 `internal-error`

**现象**：余额不足等预期内错误，玩家收到"操作失败，请查看服务器日志"，
且日志里多出一堆 SEVERE 堆栈。

**根因**：`CompletableFuture.supplyAsync` 的失败会以 `CompletionException` 包裹。
不拆包则 `cause is EconomyException` 恒为 false。

**修法**：用 `host.reply(...)`，它已经处理：

```kotlin
val cause = if (failure is CompletionException) failure.cause ?: failure else failure
if (cause !is EconomyException) plugin.logger.log(SEVERE, ...)   // 业务错误不刷堆栈
```

自己写 `whenComplete` 时记得抄这段。

## 9. 菜单 / 库存操作不生效

**根因**：在错误线程操作了 Bukkit 对象。`BalanceChanged` 在**经济线程**上同步发布订阅者。

**修法**：订阅者里必须切回主线程：

```kotlin
resources += host.events.subscribe(BalanceChanged::class.java) { event ->
    host.mainThread(active::get) { /* 现在可以碰 Inventory */ }
}
```

`MenuContext` 正是这么做的。

## 10. 关停后回调仍在执行 / 状态被破坏

**现象**：`close()` 之后，已排队的异步回访问到已释放的资源。

**根因**：`mainThread` 用 `runTask` 排队，关停瞬间队列里可能还有任务。

**修法**：`active` 闸门。每个 context 一个 `AtomicBoolean`，
`close()` **第一件事**就是 `active.set(false)`，并把 `active::get` 传给
`host.mainThread` / `host.reply`。回调执行时会重新检查，不通过就静默丢弃。

## 11. 假实体 ID 与其他插件冲突

**现状**：`RenderService` 用 `companion object { AtomicInteger(-1) }` 递减负数 ID。

**两个注意点**：

1. 它是 **`companion object`**（进程级静态），**所有 `RenderService` 实例共享**同一个序列——
   测试里创建多个实例不会重置计数。
2. 负 ID 是为了避开服务端正常正 ID。**与其他假实体插件并用会冲突**，
   需要统一 ID 分配策略（`RenderContext.kt` 启动时 `check(id < 0)` 只防耗尽，不防跨插件冲突）。

已在 `contexts/meowo-render/README.md` 记录为已知限制。

## 12. `Money` 边界用错导致误判

| 写法 | 结果 |
|---|---|
| `Money.of(BigDecimal("0.001"))` | **抛 INVALID_AMOUNT**（不做隐式四舍五入） |
| `Money.of(BigDecimal("-1"))` | 抛 INVALID_AMOUNT |
| `plus` 溢出 | 抛 **LIMIT_EXCEEDED**（不是 INVALID_AMOUNT） |
| `minus` 余额不足 | 抛 **INSUFFICIENT_FUNDS** |
| `Money.of(BigDecimal.valueOf(MAX_MINOR, 2))` | 合法（正好等于上限） |

**注意 `EconomyPolicy.fee` 的 `coerceIn`**：零余额 × 0.001 = 0，CEILING 后仍是 0，
但 `coerceIn(minimum=1, maximum=233)` 把它抬到 **1**。
所以**零余额传送也会被要求最低 1 Meo**——余额不足则传送失败并退款。

## 15. 消息改成多行后，原本通过的断言开始读错内容

**现象**：`assertTrue(payer.nextMessage()!!.contains("自己"))` 失败，
实际读到的是**上一条命令**的第二行（"当前余额 ฅ17.50 Meo"）。

**根因**：`Messages.send` 把语言文件里的 `\n` 拆成多条独立消息。
一条命令现在可能产生 2～3 条消息，而 `nextMessage()` 每次只消费一条。

**修法**：断言完第一行后清空剩余行（`drain`），或改用
`generateSequence { x.nextMessage() }.toList()` 整体断言。
详见 [06 §3](06-测试与验证.md)。

## 16. `nextMessage()` 返回 null（测试 NPE）

**现象**：刚 `dispatchCommand` 就断言消息，拿到 `null`。

**根因**：命令结果走 **经济线程 → `host.mainThread` → 主线程** 才发给玩家。
不推进调度器，任务还在队列里。

**修法**：`dispatchCommand` 之后 `flush(id)` 或至少 `server.scheduler.performTicks(1)`。
`balance()` 辅助方法内部已经含一次 `performTicks(1)`，所以 `flush` 通常够用。

## 17. 构建在 `compileKotlin` 卡死（不是网络、不是死锁）

**现象**：`./gradlew test` 长时间停在 `:contexts:meowo-xxx:compileKotlin`，
CPU 占用很低，看起来像挂死。

**根因**：和 §1 同源——iCloud 冲突副本已经堆积到第 3、4 份
（`TeleportSettings 2.class`、`RequestBookTest 4.class` …），
Kotlin 增量编译器在重复的 class 文件上空转。实测一次污染可达 **87 个**重复 `.class`。

**修法**：`./gradlew clean` 后重跑，干净状态约 24 秒完成。

**快速判别**：

```bash
find . -name "* [0-9]*.class" | wc -l     # 非 0 就是这个问题
```

**不要**去 debug 源码或怀疑 Gradle 缓存。**每次完整验证前先 clean**，这是本机铁律。

## 18. 统计测试数把 iCloud 旧快照算进去

**现象**：脚本数出 24 个测试，但真实只有 18 个。

**根因**：`build/test-results/test/` 里也会生成冲突副本
（`TEST-com.meowo.core.MeowoRuntimeTest 3.xml`），内容是**更早一次运行的旧快照**，
被 `*.xml` 通配符一起计入。

**修法**：统计时排除带数字后缀的副本：

```python
if re.search(r' \d+\.xml$', p): continue
```

同样地，**核对 jar 内容或覆盖率前先 clean**，否则读到的是上一轮产物。

## 19. ⚠️ MockBukkit 未实现的方法让测试「静默跳过」，构建还是绿的

**这是本项目最阴险的一个坑**，因为它**不报错**。

**现象**：`./gradlew test` 显示 `BUILD SUCCESSFUL`，但报告里
`skipped=8`，那 8 个测试**根本没跑**。覆盖率反而「正常」。

**根因**：MockBukkit 4.116.1 有大量未实现的桩方法，调用时抛
`UnimplementedOperationException("Not implemented")`。**JUnit 把「测试方法抛异常」
报成 skipped 而不是 failed**（异常从测试方法逸出到执行器时），Gradle 视其为非失败。

本项目踩到的两个：

| 方法 | 替代 |
|---|---|
| `BlockMock.isPassable()` | `Material.isSolid()` —— 纯枚举方法，语义等价 |
| `WorldMock.getSpawnLocation()`（新世界未设出生点时） | 先 `setSpawnLocation(...)` 再读 |
| `SimpleInventoryViewMock.convertSlot()` | 玩家**没开任何界面**时 `player.openInventory` 就是它，且 `top` 是 `null`，**任何** `InventoryClickEvent(view, ...)` 都会在构造器里炸。自建 `PlayerInventoryViewMock(player, Bukkit.createInventory(null, 9, "x")).apply { type = CRAFTING }` |

第三例的代价是实打实的：潜影盒有三个用例（含一个本轮新增的）**从来没执行过**，
却一路显示为「通过」。详见 [14-shadowbox §6](16-shadowbox.md)。

**最要命的一点**：这两处**在真实 Paper 上完全正常**，所以代码本身没错，
但你**失去了这一段逻辑的全部测试覆盖**，却从构建结果上看不出来。

**修法 / 自查**：

1. 优先用**纯枚举/纯数据方法**（`Material.isSolid`、`isAir`）而不是依赖世界的
   `Block` 方法，既能测又语义清楚。
2. **每次验证都要断言 `skipped == 0`**：

```bash
python3 - <<'PY'
import glob,re,xml.etree.ElementTree as ET
t=f=e=s=0
for p in glob.glob("**/build/test-results/test/*.xml", recursive=True):
    if re.search(r' \d+\.xml$', p): continue
    r=ET.parse(p).getroot()
    if r.tag!="testsuite": continue
    t+=int(r.get("tests",0)); f+=int(r.get("failures",0))
    e+=int(r.get("errors",0)); s+=int(r.get("skipped",0))
print(f"tests={t} failures={f} errors={e} skipped={s}")
PY
```

3. 调试时 JUnit 只在 `<skipped message="..."/>` 留一句 message，**没有堆栈**。
   想知道是哪一行抛的，就在夹具里临时包一层 `catch (e:Throwable) { e.printStackTrace(); throw e }`。

> 这个脚本已经写进 [06 §6](06-测试与验证.md)，**每次改完都跑一遍**。
> 「BUILD SUCCESSFUL + skipped>0」等于「这段逻辑没被验证过」。

## 20. ⚠️ MockBukkit 里没设置过的方块是 `GRASS_BLOCK`

**现象**：任何「这块必须是空气」「头顶不能是实心方块」的空间检查，在 MockBukkit 测试里
**永远命中拒绝分支**，看起来像代码有 bug；真服上完全正常。

**根因**：`MockBukkit` 的世界不是按原版规则初始化的——**没有被显式设置过的方块
返回 `GRASS_BLOCK`（实心）而不是 `AIR`**。所以「没放过东西 = 这里是空的」这个
在真服成立的前提，在 MockBukkit 上不成立。

**修法**：测试里把需要的空间显式设成 `AIR`，不要依赖「默认是空气」。
本项目的例子是 `MeowoRuntimeTest.clearSeatRoom`。

```kotlin
private fun clearSeatRoom(block: Block) {
    val origin = block.location
    for (dx in -1..1) for (dz in -1..1) for (dy in 1..2) {   // dy 从 1 开始，别把座位本身清掉
        block.world.getBlockAt(Location(block.world, origin.x + dx, origin.y + dy, origin.z + dz))
            .type = Material.AIR
    }
}
```

> 写这个函数时我自己先踩了一次：`dy` 从 `0` 开始会把刚放下的座位方块一起清成空气，
> 于是「所有测试都拒绝」，看起来更像代码错了。**先确认默认，再确认范围。**

## 21. ⚠️ `InventoryView#convertSlot` 会把玩家的**热键栏**重编号到储物区下面

**现象**：盒子**放在快捷栏（含主手）里时，Shift + 右键打不开**；放在上面三行储物格却正常。
用户测试时如果盒子刚好在储物格上，完全看不出问题。

**根因**：`InventoryClickEvent#getSlot()` 返回的是 `view.convertSlot(rawSlot)`，
**不是玩家以为的那个下标**。当 `view.type == CRAFTING`（玩家按 E 打开自己的背包）时，
Bukkit 的换算把玩家的背包**重新编号**：

| raw | 5–8 护甲 | 9–35 储物三行 | 36–44 **快捷栏** | 45 副手 |
|---|---|---|---|---|
| `event.getSlot()` | 36–39 | 9–35 | **0–8** | 40 |

**快捷栏被换算到了 0–8，落在任何「储物区从 9 开始」的范围之外。**
而主手就是快捷栏第 0 格 —— 也就是玩家最可能拿着盒子的那个格子。

**修法**：**不要在转换后的槽位上做范围判断**，用 raw 槽位和 view 的上半部分比较：

```kotlin
// 转换后的 event.slot 不可信；raw 槽位从 view 的上半部分开始，就是玩家自己那一半。
playerSlot = event.rawSlot >= event.view.topInventory.size,
```

这条对**所有** view 都成立，且不需要任何魔法数字：物品栏视图上半部是合成网格，
容器视图上半部是容器本身，创意模式上半部是物品栏——都符合直觉。

**怎么测才不会假绿**：见 [14-shadowbox](16-shadowbox.md) 的
`every part of the player's own inventory opens the box`。它遍历多个储物/快捷栏下标，
并且**先断言这次遍历里确实存在一个被换算到 9 以下的槽位**——
否则把遍历下标换成「安全」的那些，这条测试照样绿，却再也防不住这个回归。

## 22. ⚠️ 插件造的窗口在关闭时会被**原版退给玩家**——不主动清空就是刷物品

**现象**：往盒子里放了 10 个钻石，关掉窗口。结果盒子里 10 个，**背包里又凭空多 10 个**。
「东西放进去取出来一切正常」测不出来，只有**关闭窗口时里面还留着东西**才会中招。

**根因**：`Bukkit.createInventory(...)` 造出来的窗口**背后没有方块实体**。
Paper 的 `CraftInventoryCustom` 在 NMS 侧就是一个裸 `NonNullList`（源码注释原话：
*a standalone NonNullList with no NMS block entity backing*），所以它和箱子、潜影盒不同——
那些关掉时物品是留在方块里的。而 CraftBukkit 的关闭时序是（Paper 自己的 patch 里可见）：

```java
CraftEventFactory.handleInventoryCloseEvent(this, reason);   // ① 我们的 InventoryCloseEvent 在这里跑
this.connection.send(new ClientboundContainerClosePacket(...));
this.doCloseContainer();                                     // ② 原版在这里把容器物品还给玩家
```

**我们把内容存进了盒子，却没清空窗口**，于是 ② 又把同一批物品退了一次——**一份进盒子的同时一份进背包**。

**修法**：存完之后**无条件清空窗口**。用 `finally` 保证任何分支（存成功、盒子丢了、
写回抛异常、存的物品被退回给玩家）都走到：

```kotlin
try { save(player, session) } catch (e: Throwable) { /* 退回给玩家，绝不吞掉 */ }
finally { drain(session.window) }   // ← 这一步就是防刷的那一步
```

**清空在两种世界里都是安全的**：原版要是不退，窗口已经关了没人看得见；原版要退，
里面已经空了没得退。**先克隆再清空，顺序不能反。**

> ⚠️ 这和准本 §3.2「窗口里一个像素都不能碰」**不矛盾**，两条规则的分界是**事件**：
> `InventoryClickEvent` 在原版搬移**之前**触发，所以那里清空 = 销毁物品；
> `InventoryCloseEvent` 是关窗，**这时清空才是正确做法**。
> 把 §3.2 无差别套到 close 上，正好制造出这个刷物品的洞。

**测试怎么写**：MockBukkit 的 `closeInventory()` **不模拟**退款，所以照抄这个 bug
在测试里是绿的。必须**直接断言窗口被清空**——`window.contents` 全部为空，
因为那正是真服上会被原版再退一次的东西。

## 23. ⚠️ 一叠盒子共用一个 id → 每只都带一份内容

**现象**：背包里有**两个一模一样、没标记的潜影盒**（会叠成一格）。
Shift + 右键打开，往里放 64 个钻石，关掉。两个盒子里**各有 64 个钻石**。

**根因**：`ItemStack#amount = 2` 是**一个**物品对象。`adopt()` 给它打上 id 之后，
这一叠里的每只盒子共享同一个 id 和同一份方块实体 NBT。`finish()` 把内容写进这个
「amount=2 的物品」之后，原版按 NBT 拆栈——**拆出来的每只都带着同一份内容**。

**修法**：**拒绝打开 `amount > 1` 的盒子**并提示先拆开。
带内容的盒子在原版里本来就不可能叠，所以这只影响「一叠空盒子」这种可预见的场景。
比起冒吞物品的风险去实现自动拆叠，拒绝对玩家更诚实。

## 24. ⚠️ 用 `==` 找回被替换的物品 → 认错那只盒子

**现象**：玩家背包里有**两个完全相同、都没标记**的盒子，在不同格子。
点开其中一个，被打上 id 的却是**另一个**。

**根因**：`ItemStack#equals` 比较类型、数量和 meta。**两个没标记的潜影盒就是相等的**。
于是「把改过的副本放回原处」写成

```kotlin
when {
    player.inventory.itemInMainHand == original -> ...   // ← 命中了主手那只一模一样的
```

**修法**：**把位置作为参数传进来**，不要靠相等去猜；而且**已经有 id 的盒子根本不进
`adopt`**，也就没有「放回去」这回事了。三处调用点各自知道确切位置：
命令 = 主手，`PlayerInteractEvent#hand` = 主/副手，`InventoryClickEvent#slot` = 背包下标。

> CRAFTING 视图里 `event.slot`（**转换后**的）**就是**玩家背包下标，见 [08 §21](08-坑与反模式.md)；
> 但在 MockBukkit 里，替身视图的上半部是 9 格而不是原版的 5 格，映射会错位——
> 测试里要用 `view.convertSlot(raw)` 取期望值，别硬编码下标。

## 25. ⚠️ 尖括号不是我们画的：客户端的 `chat.type.text`

**现象**：玩家反馈所有私信都被 `<>` 包住，要求去掉。

```
<✉ Alice → Steve ✔ 你在吗> 你在吗
```

**根因（两层）**：

1. **括号来自客户端。** 当时用 `player.sendMessage(c, ChatType.CHAT.bind(name))`
   显示发言者。sender 槽位是**客户端**用 `chat.type.text` 渲染的，而它的值写死在
   客户端语言文件里：`"<%s> %s"`。服务端从头到尾没有一处写过 `<`——
   所以在代码里「剔除尖括号」当然什么都不会发生，那一步发生在组件上线**之后**。
2. **正文被传了两遍。** `privateMessage` 把**整行**（已含正文）当名字传进 `sayAs`，
   又把正文原样传了一遍。于是括号里一遍、括号后一遍。

**修法**：名字自己拼，整行自己发。

```kotlin
fun sayAs(sender: CommandSender, name: Component, message: Component) =
    deliver(sender, ChatLine.say(name, message))     // name + " " + message
private fun deliver(sender: CommandSender, message: Component) { /* sendMessage(message)，不带 chat type */ }
```

丢掉 chat type 没有损失：这些行本来就没有签名、没有真实 profile，
sender 槽位唯一买到的就是那个**我们要摆脱的装饰**。

**为什么值得单开一节**：排查它花了三轮，方向全错——先怀疑语言文件、再怀疑归一化、
最后才想到「也许不是我们画的」。**凡是渲染出来的东西，先问是谁写的**。
如果视觉不在你的字符串里，它就不在你的代码里。

**守门**：`platform/NoChatTypeDecorationTest` 扫全部 `.kt` 禁止再出现 `ChatType`
（单测抓不到：`ChatLine` 两种做法都拼得对）；`ChatLineTest` 钉住「成行文本不含 `<` `>`」
和「正文只出现一次」。完整经过见 [09 §2](09-模拟玩家发言可行性.md)。

## 25b. ⚠️ 同一个括号有**两个**来源：别只修一个

**现象**：猫说话、私信、邮箱全都没括号了，玩家公开聊天**仍然是 `<Steve> 你好`**。

**根因**：`chat.type.text` 有两条入口，上面 §25 只堵了第一条。

| 来源 | 谁在用 | 客户端拿到什么 |
|---|---|---|
| `Messages.sayAs` → `ChatType.CHAT.bind(name)` | **猫说话**、私信、邮箱 | 自己 `bind` 的 sender 槽位走 `chat.type.text` |
| Paper 的 `ChatRenderer.defaultRenderer()` | **玩家公开聊天** | `translatable("chat.type.text", displayName, message)` |

公开聊天那条我们一直**只改写了 `event.message(...)`，没动渲染器**——
所以事件里根本没有 `<>` 可删。这正是排查时最容易被骗的地方：
搜索自己的代码永远搜不到，因为它压根不在你的代码里。

**修法**：装一个自己的 `ChatRenderer`。关键在于 Paper 的这个分支
（`io.papermc.paper.adventure.ChatProcessor.complete()`，反编译实测）：

```java
key = (renderer instanceof ChatRenderer.Default) ? ChatType.CHAT : PAPER_RAW;
```

`ChatType.CHAT` 带装饰，`PAPER_RAW`（`paper:raw`）在 `ViewersOutgoingChat#adventure` 里
是 `BUILT_IN_CHAT_TYPES` 查不到的类型，于是走 `ChatType.chatType(Key)` 这个**单参重载**——
**没有装饰**。插件装的任何渲染器都不是 `ChatRenderer.Default`，所以一装就切过去了。

⚠️ 渲染器必须返回**完整的一行**（`名字 + 空格 + 正文`）。只返回正文的话，
客户端仍会给它套上 `<名字>`，变成 `<Steve> <正文>`。

> 教训和 §25 同一条，但要再说一遍：**视觉不在你的字符串里，就不在你的代码里**。
> 修掉一处就以为修完了 —— 同一个效果往往有多个生产者，挨个问「这条是谁画的」。
> 这里连续两次都是玩家的反馈才发现第二个来源。

## 26. ⚠️ 一行给两个人看，点击却只算一份

**现象**：玩家说「回复功能没上线，点一下是给自己私信」。

```
✉ Alice → Bob ✔ 在吗
```

**根因**：这行**同时渲染给发件人和收件人**（发件人要能回看自己发了什么），
但回复命令是两边共用一条的，而那条命令指向**发件人**：

- 收件人 Bob 点 `Alice` → `/meo msg Alice` ✅ 正确
- 发件人 Alice 点**自己**的名字 → `/meo msg Alice` ❌ 私聊自己

更隐蔽的一层：资料卡页脚写着「点击可私聊」，命令是 `/meo msg <这张卡是谁>`。
于是**任何人看自己的卡片再点一下，都是给自己发私信**。

**修法**：渲染时就分清读者，空命令 = 只留悬停不挂点击。

```kotlin
val reply = if (viewer.name.equals(from, ignoreCase = true)) "" else ChatLine.replyCommand(from, quote)
```

**为什么值得单开一节**：这类 bug **没有任何一条报错**，单测也测不出来——
`ChatLine` 两种情况都拼得完全正确，只有真机点下去才知道。而当时的 KDoc 里
明明写着「reply 快捷键按读者分别解析」，**注释描述了意图，不等于实现了意图**。

> 凡是「一份数据、两方可见」的界面，点击/提示就不能只算一份。
> 写着「点我就能做 X」的提示，只要读者不止一个，就至少有一个读者点出来是错的。
> 与其猜哪个读者是主角，不如让提示指向**行内已有的、无歧义的东西**——
> 比如 UUID 值本身：它就在那一行里，点它复制的一定是它。

## 27. ⚠️ 功能「真的存在」不等于玩家看得见

**现象**：回复功能报「没有生效」。查下来点击**是有的**，命令**也是对的**。

**根因**：它挂在发件人的**名字**上。没人会猜「名字可点」，更没人会猜「点了会把
回复预填进输入框而不是直接发出去」。功能存在，但**零可发现性**——在 UI 意义上等于不存在。

**修法**：把 affordance 画出来。

```
✉ Alice → Bob ✔ 在吗  ↩ 回复
```

按钮跟在正文后面，点一下预填 `/meo msg Alice `。
词和图标都放语言包（`reply-action`），英文客户端拿到 `Reply` 而不是中文句子里的英文单词。

⚠️ 发件人自己那一份**不渲染按钮**，不是渲染一个点不动的——
没有对象可回复，而**死按钮读起来就是「坏了」**。

> 和 §26 是同一个 bug 的两半：**§26 是「给谁」，§27 是「看不看得见」**。
> 两者都只能靠玩家点出来发现，代码里、测试里、单测里全都正常。
> 交互元素只要不是一眼就能认出来的，就当它不存在来设计。

## 28. ⚠️ 帮助页：占位符多传一个 0 + 列表不传 sender → 看着有内容，其实全是垃圾

**现象**：`/meo`、`/meowo help` 打开后「看起来是满的，但读不出东西」，
而且英文客户端看到的是**一半英文一半中文**。

**根因是两个独立的缺陷叠在一起**：

1. `help-line` 模板是 `"§7▸ §f{0}"`，而调用写成了 `template.format(0, label)`。
   多出来的那个 `0` 正好落在 `{0}` 上，于是**每一行**（标题、分隔线、20 行指令说明）
   都渲染成字面量 `▸ 0`——**文本全被替换掉了，但行数一条不少**。
2. 指令列表读的是 `messages.text(LIST)`，**没传 sender**，所以永远取默认语言；
   而标题、模板、分隔线用的是 `messages.text(sender, …)`。
   结果英文玩家拿到「英文标题 + 中文指令列表」。

**修法**：

```kotlin
// 1. 占位符不传多余的 0
messages.text(sender, LINE, label)          // {0} → label
// 2. 列表也带 sender
messages.text(sender, LIST).lines() …
```

**为什么难发现**：

- 一页 `▸ 0` **完全满足**「收到了多行」「没有漏占位符 `{}`」「不是空页面」这些断言。
  真正能抓住它的断言是**比对具体文案**（见 §6：断言「读者看得见的词」而不是「有几行」）。
- `HelpPageTest` 只测了 `CommandRouter` 的权限过滤，**渲染路径一行都没测**，
  所以过滤测得再细也救不了渲染。

**另一条同源的红线**：`HelpPage` 曾经直接调 `sender.sendMessage(...)`。
`Messages` 的契约写得很清楚——**自拼多行文案必须走 `sendText`**，
否则控制台会收到裸 `§`。而且要**整页合成一条**再发，不是逐行发：
逐行发会让 20 行帮助**每行都盖一个猫徽章和名字**，而整页只该有一个。

## 29. ⚠️ 先确认事件在真实时机触发，再动手

**现象**：要求「表情加进 Tab 补全，打字时能快速输入」。
按 Paper 有 `AsyncPlayerSendSuggestionsEvent` 写了一整套桥接，接进 listener，编译过、测试过——
**线上一个字都没弹**。

**根因**：反编译服务器 jar，触发点只有一个：

```
ServerGamePacketListenerImpl.sendServerSuggestions(...)
  ← ServerboundCommandSuggestionPacket     ← 命令框
```

而 `ServerboundChatPacket` 的字段只有 `message / timeStamp / salt / signature / lastSeenMessages`
—— **聊天框按 Tab 根本不发包给服务器**。那个事件在聊天场景下永远不会触发。

**修法**：删掉那套桥接，改成不需要客户端的方案 —— **唯一前缀自动补全**：
`` `sa `` 打成 😢（`sad` 的唯一前缀），`` `mo `` 原样保留（有歧义就不猜）。
外加 `/meo em` 作为唯一的完整词表。聊天框能做的补全，只有这个。

**三条通用结论**：

1. **API 存在 ≠ API 会在你的场景触发。** 事件类在 jar 里、注解能编译、IDE 能跳转，都不代表
   有人在那个时机调它。去找**调用方**，不是找**声明方**。
2. `javap -c` 找调用点比读文档快也准。`grep -rl '事件全名'` 能秒级告诉你谁在调它 ——
   答案是「命令框那一个」，问题当场就结了。
3. **写完先确认它活着。** 一段永不执行的代码比没有代码更糟：它看起来在工作，
   还占着架构上的位置让人以为功能已有。

> 同一份记忆里还有另一个同族坑：**同一个效果往往有多个生产者**（§25 / §25b 的两个 `<>`）。
> 挨个问「这条视觉是谁画的 / 这条事件谁来调」。

## 30. ⚠️ 把记忆喂进提示词，却**不**说「不许主动提」

**现象**：给猫加了会话记忆，窗口从 6 拉到 20，落盘 7 天。功能上无可挑剔 ——
猫真的记得了。代价在别处：猫开始说「你上次说过你通宵挖矿」。

**根因**：窗口是整个提示词里**最诱人的一段文字** —— 引用过、只关于眼前这一个人、
用起来像是「显得聪明」。三条都是模型伸手去够它的理由。
把历史喂进去而**一个字都不说**，等于把主动权交给模型的自发倾向：
而「你上次说过」恰恰是让一只猫看起来像**在给你建档**的那句话。

**修法**：禁令**写在诱惑旁边**，也就是引用的对话正下方，不是只写在 system 里：

```
以上是你**确实记得**的对话。但记得 ≠ 要说。
除非 Alice 自己先提起，**不要主动翻出这里的任何内容**——不要用「你上次说过」
「你之前提到」这种开头，也不要换个说法绕着提。
它们是**上下文**，不是**话题**：让它们影响你怎么答，而不是让你有话可说。
```

system 的「怎么回」里另有一条通用的 `记得 ≠ 提得起`：
**窗口可能是空的**，而空的时候猫手上还有印象和特征，照样能主动端出来。

**三条通用结论**：

1. **喂数据等于授权使用。** 任何引用过的、属于眼前这个人的内容进提示词，
   都要同时决定「能不能主动拿出来」。这个决定**不写出来**，就是默认让模型自己定。
2. **禁令的位置决定它是否有效。** 贴着数据写的那句，比一屏之外的概括管用；
   而概括必须同时存在，否则数据一空规则就跟着消失。
3. **禁的是「提」不是「记」。** 绝对化的「永远不要提过去」会被照字面执行 ——
   玩家问「我上次跟你说什么来着」，猫答「我不记得」，比献殷勤更糟。
   **豁免条件要写进提示词，并且被测试钉住**，否则哪天有人「顺手收紧一下」规则，
   猫就变成了会对玩家装傻的东西。

详见 [15 §13 记得 ≠ 要说](15-chat.md)。

## 31. ⚠️ 守卫写在内存里，等于没写

**现象**：给「玩家最后登录时间」加一条规则 —— **只能往前，不能往后**（一个乱序任务不能把时钟拨回去，
否则正在玩的玩家会因此被判定为「已消失」，当天聊天全删）。守卫用
`ConcurrentHashMap.merge(key, at) { _, old -> maxOf(old, at) }`，**测试通过**。

把它写进 SQLite 之后，单测挂了：玩家明明刚刚登录，`seen_at` 却是 10 天前。

**根因**：守卫放在了**会过期的那一层**。`pendingSeen` 里的条目一落盘就被移除，
所以下一个条目进来时 `merge` 面前**没有可比对象**，直接把旧值原样存了进去 ——
`INSERT OR REPLACE` 老老实实地照做，因为那是它被要求做的事。

守卫只挡住了「同一批尚未落盘」的乱序。而真实的乱序恰恰发生在**跨批次**：
一个排在慢写入后面的、带着更旧时间戳的落盘任务。

**修法**：合并规则必须写在**唯一真相源旁边**，不是在它上面的缓存里：

```sql
INSERT INTO chat_active(uuid, seen_at) VALUES (?, ?)
ON CONFLICT(uuid) DO UPDATE SET seen_at = MAX(seen_at, excluded.seen_at)
```

**三条通用结论**：

1. **守卫要写在真相源那一层。** 缓存 / 队列里的比较只能挡住「还没落盘」的乱序；
   落盘之后内存里就没有可比对象了，于是守卫静默退化成「谁后到谁赢」。
2. **测试必须覆盖跨批次的乱序。** 第一版的测试连着调三次 `noteSeen`，全在 flush 之前，
   测的其实是内存守卫 —— 它会过，而且**给出虚假的安心**。
   改成「落盘一次，再来一个更旧的」才暴露。
3. `INSERT OR REPLACE` 不会替你判断谁更新。它按指令覆盖；要不要拦，是调用方的责任。

> 和 §13 的「单一真相源」是同一条：**少一个真相源，少一类读合并的 bug。**
> 这次少的那一个，在守卫里。

## 32. ⚠️ 「每天 500 次」既不是一天，也不是 500 次

**现象**：给多猫猫 AI 加了调用预算，`agents.daily-cap: 500`、每玩家 20 次、10 秒冷却。
读起来是「全服每天 500 次调用」。审计 token 消耗时发现实际账单能到 4 倍，而且**几天之后**全服问不出话了。

**根因**：两个独立的错，都属于「配置项存在、上线代码不存在或数错了东西」。

1. **「每天」不存在。** `CallBudget.reset()` 全仓库零生产调用者，
   计数器只在**插件重启**时归零 —— `daily-cap` 实际是「服务器启动以来的总量」。
   额度用完的表现是「猫不理人了」，而**日志里一句原因都没有**：禁言、冷却、额度
   三种拒绝在玩家和服主眼里长得一模一样。
2. **「次」数错了对象。** 预算在**准入**时扣 1，而 `AgentRuntime.ask` 的工具循环最多 4 轮
   = **4 次 HTTP**。所以「500 次」的物理上限是 **2 000 次**。
   而 `CallBudget.acquire` 的 KDoc 从一开始就写着「Spends one **call**」
   —— **文档是对的，调用方是错的**。

**修法**：

- `advanceTo(day)` 收一个「天」而不是自己读时钟（纯函数、可测，且「一天」由调用方定义成
  **服务器本地日期**），`AgentsContext` 每小时 tick 一次。**只有更大的日期才翻篇**：
  一次 NTP 回拨或改时区曾经能让全服额度当场回满 —— 换个时钟就能花四倍预算，这是最便宜的刷法。
- 计费点搬进工具循环：`Question.mayCallAgain` 在**第一次之后的每次请求前**问一次。
  准入时那一次仍然预付，所以超额的玩家**当场**被告知，而不是排完队才等一句道歉。
  预算花光时猫把工具**已经查到的内容**说出来（那部分已经付过钱了），查不到就重复那个拒绝。

**三条通用结论**：

1. **「计数」的单位要和「花钱」的单位是同一个。** 「次问题」和「次请求」差一个工具循环的倍数，
   而差出来的部分正好落在账单上。
2. **上限类配置要有一条跨边界的测试。** 「花满之后第 N+1 次被拒」通过了，
   而「第 2 天恢复」没人写 —— 因为测它需要跨一天，而这正是它最该被测的地方。
3. **拒绝的原因要能被看见。** 三种拒绝共用一句话时，额度耗尽是**最贵也最难查**的一种故障。

## 33. ⚠️ 守卫没抓住它声称要抓的东西

**现象**：`ImpressionPrompt.acceptImpression` 里写着注释：
「A digit is refused outright, because every invented number this prompt has produced
（"去过三次", "半夜两点"）was one a reader would take as a fact.」

于是它写了 `if (trimmed.any { it.isDigit() }) return null`。

**根因**：**注释里的两个例子都不是数字。** 「三次」「两点」是汉字，
`Character.isDigit()` 对它们一律返回 false —— **那道专为拦住它们而写的检查，一个都没拦住**。

实测：喂「他半夜不睡，去过玩家的农场三次」进这条检查，它**原样通过**，
存进 `cat_impression`，再被每次提问的提示词当事实读回去。

**修法**：改成**数词 + 量词**的窄匹配 ——

```kotlin
private val CHINESE_COUNT = Regex("[零一二三四五六七八九十百千万两几半]+\\s*[次回个天次遍趟件年]")
```

**窄是刻意的**：光匹配数词会把「不一定」「一直」「第一」全拒掉，
而一条拒掉九成该留内容的守卫，最后只会被关掉。

**通用结论**：

1. **注释里的例子要拿去跑一遍。** 一条连自己文档里的反例都拦不住的守卫，
   是**看起来像防护**的代码 —— 比没有更坏，因为它让人停止怀疑。
2. **「数字」在中文里有两个写法。** 校验中文文本时 `isDigit()` 只覆盖了一半世界。
3. **守卫的测试必须用真实的坏输入。** 我第一版的测试用了一个阿拉伯数字，
   于是通过；换成 KDoc 里那句真话，它就倒了。

## 34. ⚠️ 接上一个洞之前，先看它旁边有没有洞

**现象**：`ToolContext.lookupPlayer` 默认 `{ null }`，于是
`moderation.risk` 和 `moderation.history` 这两个「传玩家名」的风纪工具
**永远解析不到人**，永远回「我不认识这个人」。

要修它很自然：把目录接上去。接完之后这两个工具第一次能用了 —— 而
**全服任何玩家都能问猫「Bob 的风纪风险分是多少」**。

**根因**：这两个工具**从来没问过 `ctx.disclose`**。它们安全只是因为解析器缺失
—— 一个**偶然**，不是一道门。一旦「修好」工具，同时就是**打开**一个隐私洞，
而且是在「让功能变好」的名义下。

**修法**：门写进**工具自己**，不依赖它的依赖项恰好坏了：

```kotlin
when (val verdict = ctx.disclose(target)) {
    is Refused -> ToolAnswer.Refused(verdict.message)   // 只有第三方会被拒；问自己永远放行
    is Allowed -> plain("风纪风险分：${risk(target)}…")
}
```

**同一次接线还带出两个同族问题**：

- `disclose` 被**硬编码**成 `{ Verdict.Refused }` —— 连「问提问者自己」都拒，
  于是 `economy.treasury` 在一台配好了它的服务器上**对所有人都失效**。
- `askerIsAdmin` 从没被赋过值，于是提示词第 6 条规则对**每一个管理员**说
  「对方**不是**管理员」，风纪工具也把管理员当普通玩家拒绝。

**顺带清掉一个长得像防线的死代码**：`commands()` 里的
`all.filter { ctx.askerIsAdmin || !isAdmin(ctx.asker) || true }` —— `|| true`
让它永远通过，旁边的 `isAdmin` 注入点也因此从未被使用。真正的大门在逐条渲染那一行。
**两个死掉的注入点一起删掉**，免得下一个读代码的人以为那里有保护。

**三条通用结论**：

1. **「这个工具坏了」和「这个工具是安全的」是两件事。** 修好之前先读它周围缺了什么 ——
   坏掉的依赖经常正扛着一道没有人写下来的门。
2. **注入点的默认值必须是「拒绝」。** `{ null }` 那种「默认什么都不给」不算门。
3. **`|| true` 出现在过滤器里，是代码在撒谎。** 它比没有过滤器更危险：
   读代码的人会相信存在一道并不存在的权限检查。

## 35. ⚠️ 三层记忆，只有两层是活的

**现象**：提示词里有三块关于玩家的信息 —— 共享特征、这只猫自己的印象、别的猫的看法。
审计时发现后两块**永远是空的**：`[your impression]` 每次都渲染成
「(你还没怎么和 Alice 说过话)」，`[what others said]` 从未出现，
`cat_impression` 表**零行**，专门写这条印象提示词的 `ImpressionPrompt` **零调用者**。

**根因**：`CatSink` 构造 `Question` 时只给了 `facts` / `locale` / `around` / `disclose`，
**从不给 `ownImpression` 和 `peerImpressions`**。
三层的**读手和写手都需要存在**，而当时一个都没有。空着的不是「某个功能」，
是**三块提示词区块** —— 每一块都在消耗 token（那句「你还没怎么聊过话」每次都发出去），
换回一句恒定的占位文本。

**修法**（`ImpressionService`）：

- **写**在玩家拿到回答**之后**、在 agent 线程上。早一步会让一次额外网络往返
  卡在「问题 → 回答」之间。
- **触发**是聊够 3 次 + 有特征统计 + 距上次超过 30 分钟。
  那个间隔是硬的：没有它，一分钟内问十次的玩家会买到十次模型调用。
- **花主动通道的钱**（`Lane.PROACTIVE`），从不动用玩家提问的额度。
- **读**按 (玩家, 猫) 且带缓存；重启后从库里取，所以「猫记得你」跨重启成立。

**第 3 层故意不做**：印象是「写给自己看的」。把每只猫的私人笔记默认塞进别人的提示词，
正是这个项目一直拒绝的那种监视。`peerImpressions` 保持为空，
直到真的有东西会去**问**一只猫对某人的看法、且当事人同意。

**通用结论**：

1. **「提示词里有这个区块」不等于「这个区块有内容」。** 断言提示词**形状**的测试全都会通过；
   要断言的是**喂进去的那一行是不是恒定的**。
2. **一个空着的功能不是零成本。** 恒定的占位文本每次调用都要发出去。
3. **「读手 + 写手」要么一起做，要么都别做。** 只做读手，得到的是一个永远为空的区块；
   只做写手，得到是一张没人读的表。

## 36. ⚠️ 压缩层不能活得比它压缩的东西久

**现象**：给猫加了「印象」——60 字、模型在玩家不在场时从聊天统计里写的私人看法。
它被存进 `cat_impression`，被每次提问的提示词当上下文读回去。
同一轮我把聊天日志的留存改成「**15 天没登录就删**」，改得很满意。

**根因**：我核对留存表时漏了一行 —— `cat_impression` 和 `player_traits` **没有留存期**。
`PlayerProfileStore.prune()` 只删 `player_report`，而 `forgetAll(player)` 有写手、
**零生产调用者**，也就是说**没有任何玩家能要求猫忘掉他**。

于是两条承诺互相拆台：

> 第 16 天，你说过的话已经删干净了；那只猫手里还留着一句**从那些话里提炼出来的**判断。

**一份压缩副本比它的来源活得久，「我们 15 天后就删」这句话就不再是真的。**

**修法**（三条，每条都是被一个具体反例逼出来的）：

1. **时钟是「最后登录」，不是「这一行多旧」。** `updated_at` 只在猫刷新意见时才动，
   按它算的话，一个**天天上线但最近没跟猫说话**的人会被忘得一干二净 ——
   而他的聊天此刻正被完整保留着。用 `updated_at` 当时钟，等于把「他没跟猫说话」
   误当成「他不在了」。
2. **「查不到」不等于「不在」。** 登录历史只覆盖日志建立之后的人，
   把「没有记录」当成「从不登录」，会在升级那天**静默清空所有老玩家**。
   所以 `lastSeen` 返回 `null` 的意思是 **unknown**，处理是**保留**。
   —— 删除别人的数据，绝不能建立在「没有证据」上。
3. **跨 context 的时钟只能问，不能各存一份。** `chat/log.db` 别的 context 读不到（红线），
   所以走 `ChatDirectoryAPI.lastSeen()` 去问唯一的权威。
   两份「他什么时候上的线」迟早不一致，而那正是保留承诺变成假话的方式。

**还有一件事当时是缺的**：这些印象**玩家看不见**。
一整套模型机制对准一个人，而「有一句关于你的话存在」这件事从未被告知。
`/meo known` 补上了这个出口 —— 用玩家自己的语言列出、**只读**，
包括那些**猫已经不存在的**留下的印象（那仍然是一句关于这个人的话）。

**通用结论**：

1. **每加一层「派生的数据」，就要回答它归谁、谁能删。** 原始数据有留存期，
   它的派生物不会自动继承 —— 而派生物往往更容易被人当成事实。
2. **改留存规则时，把所有关于一个玩家的表都列一遍。**
   我盯着刚改的那张表看得很仔细，却没看一眼隔壁那张。
3. **删除的默认值必须是「不删」。** 「没查到所以他不在了」是一种推理，
   而且是这里唯一一种会导致**静默**误删的推理。
4. **关于某个人的派生数据，要有一条给那个人看的出口。** 不能删的东西，
   至少要能看见 —— 否则它和「不存在」在对方的感受里没有区别。

## 37. ⚠️ 往提示词里补一个「事实」，先问它是不是第二真相源

`ImpressionPrompt.Request.topics` 的注释一直写着「短话题标签，**绝不是他们的话**」。
这句话描述的是格式，但真正的问题是**来源** —— 一个来源都没有，
字段默认 `emptyList()`，于是这条「你们聊过的话题：」的提示行从来没出现过。

最顺手的补法是**再调一次模型**，让它总结聊了什么。看起来完美：
它本来就懂中文语境，比关键词表聪明。

**为什么不能**（两条，各自独立成立）：

1. **它几乎让这一层成本翻倍。** 写印象本身就要一次调用，预算从 `Lane.PROACTIVE` 出 ——
   那是留给猫「主动想说」的额度。再买一次往返，只是为了把词归个类。
2. **它会幻觉，而且幻觉贴在最危险的位置。** 这个子系统的唯一实测失败，
   就是模型把统计变成了笃定的虚构（「他半夜不睡，去过玩家的农场三次」）。
   分类器要的是**同一个形状**的请求，风险完全一样，
   而它的输出会贴在那条写着「只写你知道的事」的线**下面** ——
   护栏会被它本该拦住的东西喂饱。

**修法**：`TopicTagger` —— 一张封闭词表，纯函数，零 token。
它**没有能力**返回玩家的原话：输出的每个字都写在源码那张表里。
这条承诺是**结构性**的，不是过滤出来的，所以不需要信任它每次都做对。

**词表刻意偏保守**：漏一个话题，印象只是少一点颜色；
错一个话题，就是往一个人身上写了一条假事实，而它会被存下来、被别的猫读。
所以没有裸「金」（金币是钱不是矿）、没有英文 `how`（它在 "how are you" 里）、没有裸「家」（它在大家里）。
每加一个词，都先问一句：**它出现在别的语境里的概率有多大**。

**通用结论**：

1. **「绝不是他们的话」是一句关于来源的承诺，不是关于格式的。**
   只要来源是模型，这句话就靠模型的自觉维持着。
2. **往提示词里补事实时，先数它离「事实」有多远。**
   直接从原文抽取 > 规则归类 > 模型总结 —— 每往右一步，就多一层幻觉面，
   而且是贴在最不该出现幻觉的位置上。

## 38. ⚠️ 隐私指令里，「没问到」被写成了「0」

`/meo forget` 要如实报告每张表删了几行。这条是对的，而且是可以被钉住的 ——
玩家唯一能核对的东西就是这些数字。

写第一版时我这样处理 chat 那一半：

```kotlin
runCatching { services.load(ChatDirectoryAPI::class.java)?.forgetPlayer(id) }.getOrNull() ?: 0
```

三个不同的状态塌成了一个 `0`：**chat 没启动**、**chat 抛异常**、**真的没有记录**。
前两种是 *unknown*，第三种才是 *absent*。

这跟 §36 第 2 条是同一条规矩，我自己在写的时候犯了：
**绝不在「没有证据」上得出结论** —— 删数据时它会导致误删，
**报告数据时它会导致谎报**，而且是同一个动作里的一行 `?: 0`。

**修法**：`Int?`，`null` 单独走一条 `forget-partial` 消息，
明说「聊天记录这次联系不上，所以它删没删我没法说」。
半完成比假装完成好，因为玩家会以为还有东西留着，会再问一次。

**顺带一个刻意的「没删」**：`chat_active`（登录时间）**不删**。
它是「在场」不是「记忆」—— 忘记某人说过什么，和假装他从未来过不是一回事；
而且他下次上线这行会被重写，删了白白让留存扫描失去唯一可靠的信号。
「什么都删干净」听起来更彻底，但**删掉一个玩家仍然在场的证据，是在对他撒谎**。

**通用结论**：

1. **`?: 0` 是一种推理。** 在任何对用户复述计数的路径上，它都是一条没有被承认的推理。
2. **报告里的 unknown 和删除里的 unknown 一样危险** ——
   一个让玩家误以为还有东西，一个让玩家以为已经没有东西。
   两个方向都要留一个出口。
3. **「删干净」不是目标，「删的是记忆」才是。**
   把在场记录一起删掉，是拿诚实换了个更好听的结果。

## 39. ⚠️ 「删干净」的删除权，和销毁证据只隔一个 `WHERE`

`/meo forget` 第一版是这样删投诉的：

```sql
DELETE FROM player_report WHERE subject=? OR author=?
DELETE FROM work_order   WHERE subject=?
```

理由写在 KDoc 里，而且**听起来无懈可击**：`work_order` 全项目根本没有删除路径，
删了投诉却让纪律阶梯还握着一行关于这个人的记录 —— 那是「留着派生态的删除，不叫删除」。

**方向反了。** `subject=?` 命中的是**别人写的、关于他的投诉**。
那是别人的话，不是他的记忆。而且投诉刚写入时是 `state = "OPEN"` —— **还没人审过**。

所以第一版实际提供的是：**一个正在被投诉的玩家，打自己的名字，就能把那条没人看过的指控，
和它将要爬的那几级阶梯，一起抹掉** —— 然后命令还会如实告诉他「删了 N 条」。

同一个 KDoc 的前半句和后半句打架：
前半句说「删除不能留下派生态」，后半句说「他提交的报告也要删」；
**两边都对，但都没覆盖「别人对他的评价不属于他」**。我写的时候只想到权利那一半。

**修法**（三层，每层都必须）：

1. **删** 他自己的：印象、traits、**他提交的**投诉。
2. **标记** 别人的：投诉进 `FORGOTTEN`、工单进 `WorkOrderState.FORGOTTEN`。
   行还在库里（不重写历史），但**退出使用** ——
   `reportsAbout` 过滤掉它，`WorkOrderLadder` 的终态集合让它无法被爬升。
3. **说出来**：`forget-kept` + `forget-kept-hint` **只在真有东西留下时**出现。
   玩家无法分辨「删了」和「还在库里」时，命令就是在骗他。

**顺带暴露的两件事**：

- **`WorkOrderState.SELF_RESOLVED` 从建起就没有任何调用者**，
  而且 `next()` 的守卫里没有它 —— 真写进去，阶梯会**从一个已经结束的状态继续往上爬**。
  `openWorkOrders` 恰好只筛 `state='OPEN'`，所以这个洞被掩盖着。
  守卫改成穷举的 `TERMINAL` 集合，测试也改成遍历枚举 —— 新加一个状态会**编译不过测试**，
  而不是安静地漏掉。
- **限流不能跟着一起被「洗掉」。** `countSince`（一个作者一天能提交几条）
  原本走 `reportsAbout`。标记之后，被投诉者一执行 `/meo forget`，
  投诉人的配额就刷新了 —— **一个能被第三方重置的限流不是限流**。
  限流算的是**作者的行为**，所以单独走 `reportsByAuthorSince`，不过滤 `FORGOTTEN`。

**通用结论**：

1. **「关于某人的数据」和「某人关于别人的数据」不是一回事。**
   `WHERE subject=?` 和 `WHERE author=?` 在删除场景下**指向两个不同的权利**，
   把它们写进同一个 `OR`，就是把两个权利当成一个。
2. **一个自助入口如果能删掉别人的记录，它就是一个特权入口。**
   判据不是「谁触发的」，是「**删掉之后，谁失去了什么**」。
3. **标记 vs 删除，是这类功能的分界线**：前者退出使用、保留历史、可被管理员看到；
   后者不可逆。自助命令只该有前者。
4. **状态枚举里躺着一个没人写的值，比没有这个值更危险** ——
   它的名字暗示它安全，而守卫可能没把它算进去。
5. **限流、计数这类「行为记录」不要复用「内容查询」的过滤条件。**
   主体删自己的数据，不该顺带给第三方洗掉记录。

## 40. ⚠️ 「免费」不要用「绕过」来实现；「替别人操作」不是「同一个 player」

给 `/meo home` 加管理员能力（看别人的家、替别人设家）时，撞上两件看起来是小事、
实际都会静默出错的事。

### 一、免费 ≠ 不结算

「管理员操作不收钱」最顺手的实现是**跳过结算**：不调 `reserveTax`，直接 `store.stage`。
代码短一半，看起来也更安全。

**但那条免费路径就成了唯一不留痕的路径。** 玩家的每一次改家都会在 `teleport_charges`
和 `eco_treasury` 留下 `reason=HOME_SET` 的一行；管理员的改动什么都不留。
两年后回头查「谁动过这个基地」，答案取决于走的是哪条分支。

正确做法是**零额度，照走**：`TaxAssessment(rate=0, minimum=0, maximum=0)`。
票据、账本行、回滚全都照常发生，`fee=0` 如实记着。
**免费是一个金额，不是一条捷径。**

（`minimum=0` 之所以真的合法，是因为 `amount()` 是 `.max(minimum).min(maximum)` ——
两端都是 0 时结果就是 0，不需要为它单开一条特例分支。）

### 二、`player` 在「替别人操作」里是两个人

`saveLocation(player, home, old)` 里每一个 `player` 都默认了一件事：
**付款人、传送锁的持有者、收到报错的人、缓存写入的键，是同一个人。**

管理员替 Bob 设家时，这四个身份分成了两组：

| | 管理员 | Bob |
|---|---|---|
| 付款 | ✅ | |
| 传送锁 / 报错 | ✅ | |
| 家这一行的归属、上限、缓存 | | ✅ |

代码原来长什么样，就会在哪一处悄悄替错：
`cache[player.uniqueId]` 会把家写到**管理员**的表里（他看不见，但 Bob 看不见）；
`capacity(player.uniqueId)` 会用**管理员**的上限卡 Bob 的槽位；
`reserveTax(ticket, player.uniqueId, ...)` 会在没想过的地方扣钱。

**修法**：签名变成 `saveLocation(actor, home, old, owner = actor.uniqueId)`，
两个身份从参数上就是分开的，并且 KDoc 写清各自由谁承担。

### 三、附带的一条：`getOfflinePlayer(String)` 是不能用的

「管理员最需要的场景就是替**离线**玩家修家」—— 而 `Bukkit.getOfflinePlayer(String)`
可能阻塞在 profile 查询上，并且会为一个从没来过的名字**凭空造一个档案**。

用 `getOfflinePlayerIfCached(String)`：只认服务器已经见过的名字，
见过的（包括已离线的）都能改，没见过的失败并说一句话。

判据是：**凡是有「异步 / 可能阻塞 / 可能凭空创建」之二的 API，
在一个本来就有同步版本可用的地方，就不要用。**

**通用结论**：

1. **免费的实现方式，决定了它留不留痕。** 「跳过这一步」比「这一步的金额是 0」危险得多。
2. **一旦允许「替别人操作」，`player` 这个词就不再是一个人。**
   在单主体代码里它处处成立，所以这个洞不会在编译期或 review 里出现 ——
   只在把第二个主体接进来的那一刻出现。
3. **离线能力要用缓存版实现。** 能阻塞的 API 和会凭空造数据的 API，
   在这里往往是同一个 API。

## 41. ⚠️ 帮助页漏掉的每一条，都在某个人的盲区里

重写 `/meo help` 时逐条比对了**路由**和**帮助列表**，发现的不只是排版问题：

| 路由 | 帮助页里有吗 |
|---|---|
| `back` / `replay` / `render` / `em` / `help` | **没有** |
| 页脚却在宣传 `/meo replay #编号` | 而它自己不在列表里 |

**一个宣称「列出命令」却只列了 19/25 的页面，比一个短页面更糟** ——
因为漏掉的正是你这次来查的那条。而页脚宣传了一条列表里没有的命令，
等于用另一处文案承认了列表不完整，却没有据此补上。

第二个问题更隐蔽：**每行只写 `info`、`eco`、`msg`，没有前缀**。
帮助页唯一的工作就是让人把命令粘回聊天框，而这一页没有一行能粘。
（`/meo <route>` 对**所有**路由都成立，因为根别名 `meo` 的前缀是空的 ——
这是能安全把前缀写死的前提。）

### 重写时顺手挖出来的：`meowo.teleport.back`

把「代码里当权限用的字符串」和「plugin.yml 里声明的节点」做了差集，
**全项目只剩一个没声明**：`meowo.teleport.back`。

Bukkit 对**未声明**的节点按默认组解析，也就是 `OP`。所以：

- 功能写了、路由注册了、`/meo back` 存在；
- **只有管理员能用**；
- 帮助页忠实地把它藏起来了（因为它确实只有管理员能跑），
  Tab 补全也这么藏，命令处理器也这么拒 —— **三处全都在读同一个错误答案，并且彼此一致**。

这就是为什么它能一直躺着：**产品内部没有任何一处会说「这里有问题」**。
而一个在描述文件里找不到的权限，别人也**没法授予**。

修法两条：声明它（`default: true`，它和 `/tpa` 是同一个功能家族），
以及加一条回归测试 —— 遍历所有活动 context 的所有路由，
断言它们的权限都在 `plugin.yml` 里声明过。
为它给 `CommandRouter` 加了 `permissionOf(name)`，给 `MeowoRuntime` 加了只读的
`router` / `activeContexts`：这是**唯一需要「路由」和「描述文件」同时在手**的检查。

**通用结论**：

1. **「帮助页列了 N 条」和「插件有 N 条命令」是两个数，必须定期对账。**
   路由一加，帮助页就悄悄过期了 —— 而且没有任何东西会告诉你。
2. **帮助页上出现的每一条，都必须能原样粘回聊天框。** 不能粘的行等于装饰。
3. **权限过滤的一致性会掩盖权限本身的问题。** 当帮助、补全、处理器
   **全都给出同一个答案**时，那个答案很可能一开始就是错的 ——
   大家互相印证，反而没人去核对源头。
4. **「产品内部没有报错」不等于「配置是对的」。** 未声明的权限不会抛异常，
   它只是安静地取一个你从没想过的默认值。

## 42. ⚠️ 聊天消息是客户端给的 Component，不是「一段文字」

问「聊天系统能不能阻止玩家发的单击执行」的时候，答案是**不能**，而且不是「可能有风险」——
是实测过、真的能提权。

### 一、`run_command` 会原样活到广播行

客户端发来的是 **Component**，而 Component 能带点击事件。原版客户端只发纯文本，
**改过的客户端可以往某一个词上挂 `ClickEvent.runCommand("/op attacker")`**。

点击处理跑在**点击者**的客户端、用**点击者**的权限。所以攻击者自己不需要任何权限：
发一条看起来正常的消息，管理员点其中一个词，管理员就把自己 OP 给了攻击者。
**点的人越多，拿到权限的人越多。**

实测（`ChatLine.publicLine` 前后各序列化一次）：

```json
{"click_event":{"action":"run_command","command":"/op attacker"},"text":"CLICK HERE"}
```

`ChatLine.clickable` 只是给**根节点**加了自己的 `suggest_command`，
它对子节点自带的事件**一个字都没动**。而整条消息是嵌套组件，
所以 `clickEvent()` 设的是一个节点，其余节点原封不动。

修法：`ChatLine.withoutEvents` **递归**剥掉 `ClickEvent` 和 `HoverEvent`，
两处调用 —— 聊天入口（挡住世界）和 `clickable`（挡住下一个没想起来的人）。
「门要写进工具本身」这条在这里不是比喻：**一个「body 从这里进来」、
「来什么渲染什么」的行渲染器，不是渲染器，是转发器**。

### 二、`§` 能在自己的消息里上色

`§` 是 U+00A7，**不是控制字符**，所以 `ChatPipeline.normalise` 留着它，
而管线的装饰输出会交给 legacy 反序列化器 —— 那里 `§c` 读作「从这里开始红色」。

实测：``§c§lADMIN 管理员 §r`sad` `` → 管线输出 `§c§lADMIN 管理员 §r😢` → **红色加粗**。

**它只在装饰改动了字符串时才发作**，所以例子里必须有个 emoji：
没有 emoji 也没有 markup 的消息原样透传，保持纯文本。
这让它**读代码看不出来** —— 拿一个光秃秃的 `§c` 去测，看起来是安全的。

修法是**删掉 `§`**。这里有个坑值得单独记：**「把它加倍」是错的**，
而且错到不实测就发现不了 —— `§§c` 反序列化出来是「一个字面 `§` + 红色」。
两个 `§` 不是转义，是一个 `§` 加一个代码的开头。所有「聪明」的变体都一样：
去掉 `§` 留下 `c`，同一条消息里**更早的**那个 `§` 就活了；
两个都去掉，`§§ca` 会剩下 `§a`，深绿色。
**没有任何一种排列既能惰性、又还长得像一个 `§`。**

所以玩家打 `§c` 会看到 `c` —— 这正是原版会给他的，没人会被误导那段文字是谁的。

### 通用结论

1. **「用户输入」要先问它是什么类型。** 字符串有转义，组件有事件；
   两者被同一个变量接住的时候，防护写在哪一层就成了安全问题。
2. **净化要递归，而且要写在工具里。** 只处理根节点等于没处理 —— 攻击载荷天然住在子节点里。
3. **「加了防护」必须实测它真的挡住了。** 本轮两次凭直觉的修法（倍增 `§`、
   只给根节点加 click）都是**实测**否掉的；不测就会带着一个假的安全感上线。
4. **过滤条件要挑对触发条件测。** `§c` 测不出来，``§c`sad` `` 才测得出来。

## 43. ⚠️ 「过闸门」不等于「过滤」：判定和打码是两件事

`/meo msg` 的两条私聊通道都只调了 `ModerationGate.decide()`，
代码注释写着「the same gate, the same rules … the single most important line in the file」。
**这个说法本身制造了漏洞。**

`ModerationGate` 只判定。它对命中的过滤词返回：

```kotlin
ModerationDecision(ModerationAction.REDACT, "filtered", hits = redacted.hits)
//                                                              ↑ replacement 默认 null
```

然后旧代码 `Reference.parse(decision.replacement ?: text)` —— `replacement` 是 null，
于是拿回**原文**。真正执行替换的 `RuleSet.redact()` 只有 `ChatPipeline` 调。

结果：配置里每一条字面量和正则过滤词都只对公开聊天生效。
玩家想让某个词出现在屏幕上，把它打进私聊，两条通道（对猫、对玩家）都照办。

修法是让私聊走整条 `pipeline.process()`，代价是私聊也会吃到 emoji 和 markup。
**这是主动选的交换**：两条不会漂移的通道，比两条今天恰好一致的通道值钱；
「记得在每个新调用点补一次 `redact`」正是刚刚失败的那个办法。

变异运行（把两处改回只调闸门）：

```
→ §8#lmem§r §7✉§r meov0 §8→§r Bystander §a✔§r 我们去 违禁词 吧
→ [我们去 违禁词 吧]
```

### 通用结论

1. **「过滤器」「审核器」「闸门」不是同一个词。** 判定（要不要放行）和替换（把词换成
   `***`）是两步。只实现第一步然后叫它「过滤」，等于实现了一个只会点头的过滤器。
2. **返回 `null` 的可选字段要问「调用方拿 `?:` 兜底的是什么」。** 这里兜底的是**原文**，
   于是每一个 `REDACT` 都静悄悄地退化成 `ALLOW`。空值不是中性的。
3. **注释里写着「这是最重要的一行」的那一行，本身就是一个危险信号。**
   它把代码标记成「已复查」，而复查的判据又恰恰是那句注释。真正的复查要**把行为改回
   旧样子跑一次**，看测试会不会红 —— 本轮就是这么做的。

## 44. ⚠️ 两套格式词汇同时在跑，门禁一条都没禁

`MarkupFormatter` 输出 BBCode（`**粗体**` → `[b]粗体[/b]`），
渲染路径却交给 `LegacyComponentSerializer`——它只认 `§`。
两套词汇谁也不读谁，于是玩家打 `**粗体**`，看到的是字面 `[b]粗体[/b]`。

这不是笔误，是 KDoc **论证过**的：

> Output markers use the same vocabulary as the input, so a result can be re-parsed or
> handed straight to a legacy `§` serializer without a second translation table.

`[b]` 不是 `§l`。这句话自相矛盾，它为「用 BBCode」提供了理由，
于是下一个人会照着它再做一遍。**错误结论写在文档里，比没有文档更贵。**

### 为什么不是把 markup 改成输出 `§`

那是最小改动，看着也对。**它是错的**：
`§` 是 U+00A7，不是控制字符，能穿过 `normalise`，
于是「玩家正要发出去的字符串」和「一段序列化指令」再也分不开——
玩家打 `§c§lADMIN` 就能拿到红色加粗、看起来像服务器自己说的话。

**格式码属于写这个字符串的人。** 所以按所有权切：

| 函数 | 用途 | `§` 是什么 |
|---|---|---|
| `ChatLine.plain` | 语言包 | **预期的格式**（运维写的） |
| `ChatLine.body` | 玩家 / 模型产出 | **一个字符** |

`body` 是渲染层唯一的正文解释器，只认 `[b]` `[i]` `[u]`，
而且**只认成对的**——`[b]` 后面没有 `[/b]` 就是字面文本。
这既让猫可以回答关于这套 markup 本身的问题而不把自己那句变粗，
也让玩家打出的方括号不会被吃掉一个字符。

### 通用结论

1. **一个字符串不能既是数据又是它的序列化形式。** 中间没有类型区分时，
   「谁写了这串」就必须变成一个函数签名（`plain` vs `body`），
   否则每个渲染点都要重新判断一次。
2. **「改一个字让它对上」要问它在哪个信任边界上。** 这里改的是把玩家的字符合法化进一种
   会被解释的格式——不是对齐，是开门。
3. **未闭合的标记必须原样保留。** 这是 `MarkupFormatter` 已经遵守的规则，
   解释器也得遵守，否则它会吃掉玩家真打出来的字符。
4. **架构门禁没禁的，就不是约定。** `verifyArchitecture` 原来只查
   `org.bukkit` / `io.papermc` / `taboolib`——**Adventure 不在里面**。
   domain 源码根一个 kyori import 都没有，但那是自觉，不是门禁。
   已于 2026-10-08 把 `net.kyori` 补进 `build.gradle.kts` 的 `forbidden` 列表并实测会拦。
   教训本身比补丁重要：`15-chat.md` §2 和 `01` §1 **早就写着**这条规则，
   文档说「连 Adventure 也不能碰」，门禁却只查另外三个 ——
   **规则读起来像被强制、实际没被强制，比没有规则更糟。**

### 一条被实测否掉的「发现」

分析时我判断 `ChatContext` 那个序列化器 `.hexCharacter('#')` 配
`useUnusualXRepeatedCharacterHexFormat()` 会让 `&#ff0000` 直接上色，
等于**第二条**注入路径。写完代码注释才去测：

```
&#ff0000ADMIN      -> coloured=false   （两种 reader 都一样）
§#ff0000ADMIN      -> coloured=true
§cADMIN            -> coloured=true
```

`&#ff0000` **不是转义**，缺的就是那个 `§`。所以 hex 配置没有独立的安全后果，
只是一处装饰。**这意味着我已经照着错误结论改了一行代码注释**——
真实存在的洞只有 `§` 一个，而且卡在同一个 `withoutSections` 上。

## 45. ⚠️ 死代码里最危险的不是没人调用，是「注释承诺了一个不存在的消费者」

一次全仓零引用扫描（统计每个声明在 main + test 的引用数）找出 16 条真候选。
其中三条的注释是这样的：

```kotlin
/** How many players this log knows about. For diagnostics and tests. */   // 零引用，测试也没用
/** Test seam: the team a player currently belongs to, or null. */          // 零引用，测试也没用
/** Why that destination was recorded, so the command can say which kind of "back" this is. */
fun lastCause(): String = cause                                              // 命令从来没说过
```

**注释写着「供测试使用」，而测试里没有它。**
这比普通的死代码更糟：它把一行代码标记成「已被需要」，
于是没人会去查它是不是真的接上了——注释本身就是那个证据。

### 真正危险的那一条：隐私规则的第二份复制品

`Guard.mayReadProfile` 是 `Redaction.verdict` 的**第二份实现**，零引用（含测试）。
它不仅没用，还**三处都和生效的那份不一致**：

| 情况 | `Redaction.verdict`（生效） | `Guard.mayReadProfile`（死的） |
|---|---|---|
| 自己 + 已关闭 profiling | 拒绝 | `subjectProfiling \|\| true` → **放行** |
| 管理员 | `FULL` | **永远不返回 `askerIsAdmin`** |
| 死分支 | — | `else` 不可达；`CONSENT` 分支已被前面的检查强制为 true |

也就是说：谁哪天「顺手把 `mayReadProfile` 接上」，
一个关闭了 profiling 的玩家就能读回自己的档案，管理员则完全读不到人。
**第二份隐私规则不是冗余，是第二个正在等着被接上的答案。**

反过来，**生效的那份一个测试都没有**——注释长在被删掉的那份上。

修法：删掉复制品，在 `Guard` 上留一句指向 `Redaction.verdict`，并补 `RedactionTest`（11 条）
把规则逐条钉住。**注释要长在会被调用的那个函数上。**

### 没删的那两类

零引用不等于该删。这次留下的是**写完了但没人触发**的完整设计：

- `CatSink.offerProactive` + `Lane.PROACTIVE` + `droppedProactive` —— 整套「猫主动开口」机制
- `ActionCounters` —— 主代码从不构造，只有测试在用

删掉一半会把设计毁掉，接上哪个又是**产品决定**，不是清理。
同理，扫描还报出 7 个 `@EventHandler` 和 `MeowoCore`（`plugin.yml` 的 `main:`）——
它们零引用只是因为 Bukkit 靠反射注册。**「零引用」是候选，不是判决。**

### 第二遍：常量同样会漂移，而且漂移得更贵

扫完函数再扫常量，`/meo msg` 在**主代码里被写了四遍**：

| 位置 | 状态 |
|---|---|
| `Messages.DM_COMMAND` | 在用，但注释写着「Written once so the help copy and the click agree」 |
| `ChatLine.DM` | 在用，注释写着「matches `Messages.DM_COMMAND`」 |
| `ChatService.REPLY_PREFIX` | 零引用 |
| `ChatCommands.REPLY` | 零引用 |

更要命的是 `Messages.systemName` **把 `ChatLine.msgCommand` 又手写了一遍**
（`"$DM_COMMAND $name "`），而同一个文件里另外三处都在正确调用 `ChatLine.msgCommand`。

**两处注释都在承诺唯一性，而唯一性早就没了。** 改私聊命令名的话，
每一行回复按钮都会变成一条不存在的命令，而**没有任何东西会失败**——
要等玩家点下去才知道。

修法：`ChatLine.DM` 成为唯一来源，`systemName` 改调 `ChatLine.msgCommand`，
两份注释改成解释「为什么只有一份」。**注释保证的是意图，结构保证的是行为。**

### 通用结论

1. **注释里出现「供 X 使用」时，去 grep 一下 X。** 那是待验证的断言，不是说明。
2. **一条规则只能有一份实现。** 尤其是隐私规则和权限规则。
3. **给生效的那份写测试，不是给看起来像入口的那份。**
4. **零引用先分类再删**：反射注册的、只被测试用的、写完没接线的、真正的死代码——四类处理方式完全不同。
5. **同名同值的常量要收成一个。** 注释写着「matches」的两份，不是两份，是一份约定和一个隐患。

## 46. ⚠️ 「写完了、也测了、就是没人调」——变异运行是唯一能发现的手段

主动发言功能（猫在玩家用了自己的指令后主动搭话）在这次之前的状态是：

- `CatSink.offerProactive` —— 实现完整
- `AgentScheduler.Lane.PROACTIVE` / `droppedProactive` —— 队列策略完整
- `CallBudget` 的 `Lane.PROACTIVE` 份额与退款 —— 完整
- `Guard.proactive(...)` 九个门槛 —— 完整且有单测
- **调用者：零**

**变异运行**（把整个触发器改成 `if (true) return`）在端到端测试补上之前，
**全仓库测试全绿**。每一层单测都通过，因为每一层都只测自己那一段——
它们测的是「函数存在时它对不对」，不是「它有没有被用」。

这不是测试写得不好，是**这类缺陷在单测层面不可见**：
一个函数可以有一百条测试、覆盖率满分，同时零调用者。

### 补端到端测试时踩到的一个更值钱的发现

断言「猫尝试开口了」需要一个可观测量。原本没有——
`onRouteRun` 返回 `Unit`，`offerProactive` 的结果没人接。
于是加了 `AgentsContext.proactiveOffers`：

它数的是**尝试**，不是成功，因为拒绝它的三个闸门
（队列 / 额度 / 排队）都各自上报，不在这里。
而这个数字对运维也有用——**「猫从不说话」和「猫一直被拒绝」在服务器日志里长得一模一样**，
只有这一个计数能区分。

### 通用结论

1. **单测证明函数对，不证明函数被用。** 加一条变异：把接线那一行改坏，
   看有没有测试变红。没红就是缺端到端测试。
2. **「没人调用」不是靠读代码发现的**，是靠统计全仓引用数发现的——
   包括测试里的引用。测试引用过它，只会让它**看起来**更没必要删。
3. **触发器要有一个可观测的计数**，否则「不触发」和「触发了但被拒绝」永远分不开。

## 47. ⚠️ 「用原版 X 的效果」会被读成「做一个像 X 的效果」

飞行粒子要的是**原版去铜锈的那个粒子**。做成了自己画的：三段相位（锈 → 被剥 → 残留）
配一套手挑的褐色/钢灰/青色 dust。

错得很彻底，而且**错得看起来很用心**——它是蓝的，它在除锈，它甚至有「铁锈被剥掉」的故事。

## 失败的不是常量，是理解

没有人会写下 `COPPER_SCRAP` 然后上线。
**真的失败是把需求读成了「要一个除锈的观感」，然后画出一个更像除锈的东西。**

而它之所以能一路走到验证通过，是因为**没有任何测试会失败**：
自造的相位、颜色、尺寸全部自洽，粒子照常生成，测试照常绿。
评审看到的「蓝色除锈特效」和需求里的「蓝色除锈特效」**字面完全一致**。

## 修法：把「用哪个」变成具名值加测试

```kotlin
object FlightEffect {
    val PARTICLE: Particle = Particle.SCRAPE   // 有名字、有测试、换掉就红
}
```

于是下一次有人想「优化」这个效果时，测试会告诉他：
这是原版的，换掉就不是你要的东西了。

顺带一条实测：**`COPPER_SCRAPE` 不存在**。paper-api 26.2 里只有 `SCRAPE` 和
`COPPER_FIRE_FLAME`——最直觉的名字不是真的。用 `javap` 对着 jar 看一眼，比想三分钟便宜。

## 通用结论

1. **「用原版的 X」≠「做一个像 X 的」。** 需求里的动词是「用」，不是「做」。
2. **自造的替代品不会被现有测试抓住**，因为它自洽。抓住它的是**把选择具名化 + 给它一个测试**。
3. **字面一致不等于需求一致。** 交付物和需求的措辞长得一样，是这类错误能活下来的原因。

## 48. ⚠️ 「区块已加载」不是「区块还在」——传送只在离家近时成立

**现象**：玩家反馈 `/meo home` 只有在**家附近**才回得去，离得越远越失败，失败后费用退还、
聊天框只得到一句「操作未完成」。用 `force` 也一样。

**根因**：传送的三步各错了一点，凑成了「距离一远必失败」。

1. **加载不等于持有。** `World.getChunkAtAsync(x, z, true)` 在加载完成时就释放自己的 ticket，
   而一个不在任何玩家视距内的区块**没有任何东西持有它**——区块系统随时可以把它卸载掉。
2. **倒计时给了它三秒钟被卸载。** home 走的是「先加载 → 倒计时 3 秒 → 再传送」，
   三秒足够一个远端区块被卸载。
3. **传送那一刻还要求它已加载。** `isChunkLoaded(...) && player.teleport(...)` 会直接拒绝，
   于是 `moved=false`，退款，`home-failed`。近距离能回，是因为家在视距内，
   玩家的视距 ticket 顺手替它挡着卸载。

**为什么 force 救不了**：force 跳过的是**方块安全检查**，不是**区块是否在场**这道门。
这两道门长得像，玩家看到的却是同一条消息。

**修法**（两半，缺一不可）：

- 传送本身换成 `player.teleportAsync(destination, TeleportCause.PLUGIN)`。
  Paper 会把「加载目标区块 + 移动」合成一步、都放在 tick 之外做，
  那一瞬间区块在不在驻留就不再是插件的问题。`SpawnContext` 与 `TeleportContext`
  **早就**是这么写的——`TeleportContext` 的注释原话就是「同步传送到一个已卸载的区块，
  要么在 tick 上生成它、要么失败」。
- 从**开始加载之前**就 `addPluginChunkTicket(x, z, plugin)` 把它钉住，
  直到这次 flight 结束（到达 / 取消 / abort / close）在 `release` 里还回去。
  顺序很重要：加载完再拿 ticket 已经晚了。

**顺带一个 Paper 26.2 的签名**：`addPluginChunkTicket` 现在要第三个参数 Plugin，
两参数的写法编译不过——用 `javap` 对着 jar 看一眼比猜便宜。

**连带要注意的**：异步传送的回调**不在主线程**，而 `flights` / `busy` / 标记同步全是主线程状态。
结算必须整体搬进 `host.mainThread(active::get)`，并且用 flight 身份校验挡住二次结算。

**自检**：`find . -name "* 2.class"` 顺手跑一下。iCloud 会在 `build/` 里造出
`SeatPlacementTest 2.class` 这种冲突副本，Gradle 报的是
`Could not execute test class 'X 2'`——**和代码无关**，`./gradlew clean` 即可（见 §1）。
统计测试数时还要额外排除 `TEST-Gradle#20Test#20Executor#*.xml`，那是 Gradle 自己的执行器文件。

## 49. ⚠️ 测试替身与渲染器不一致：点「确定」没反应，点到了别人头上

**现象**（两个，一起来的）：

1. 家的确认页点「确定」，**什么都没发生**——家没存下来，测试卡在
   `pump { context.homes(...).any { ... } }` 上超时。
2. 管理员点自己的确认页，结果**普通玩家**的家被存下来了，而管理员一个家也没有。

**根因**：`FakeUI` 与 `UIRenderer` 在两处不一样，而替身是「照着渲染器写的」——它一旦开始漂，
测试就会测一个服务器上并不存在的行为。

| 规则 | 渲染器（真的） | 替身（曾经） |
| --- | --- | --- |
| override 的 action 为空 | `withActionFrom(button)`：**回退到配置里的 action** | 直接用 `shown.action` → 空串 → 派发了空指令 |
| 指令以谁的身份执行 | `player.performCommand(...)`，**页面的拥有者** | 固定一个玩家 |

第一条的后果是「看起来能点、点了没反应」：模块给的 override 只改文案（图标、名字、lore），
动作仍然来自 `ui.yml`，而替身把那个动作丢了。第二条的后果更隐蔽：**第二个玩家的点击被算到第一个
玩家头上**，于是一个玩家替另一个人存了家。

**修法**：替身照抄渲染器的两条规则，别自己发明。

```kotlin
// 1. 内容型 override 不该把动作也带走
shown.action.ifBlank { button.action }

// 2. 派发时把「谁在看这一页」一起交出去
var dispatch: (UUID, String) -> Unit = { _, _ -> }
```

**怎么测才不会假绿**：确认页的测试必须**真的点那两下**（点确认、看家有没有出现），
而不是只断言「页面标题对了」。标题对了只说明页面开出来了，说明不了「确定」这个格能干活。

## 50. ⚠️ 界面给了 16 个图标，路由却只认其中两种

**现象**：家园总览里的「菜单物品图标」页列着 16 个物品，点上去**没有反应**——图标不会变，
聊天里也没有任何话。

**根因**：路由的 `icon` 动词只认 `default` / `bowtie`（那是**定位栏的两种样式**），
而图标页派下来的命令是 `home gui icon <编号> <物品名>`。参数是物品名，路由不认 → 落到 usage
分支 → 玩家看到一句用法，而不是「图标已改」。

**为什么会这样**：数据、存储（`encode`/`decode` 里带着 `item`）、界面（16 个格子的列表）、
菜单总览里用 `home.item` 画图标——**四处都在**——唯独路由少了一个分支。于是功能是「做了一半」：
数据能存下来，界面能列出来，没有任何一条路能把值写回去。

**修法**：路由按**参数长什么样**决定是哪一种：

```kotlin
"icon" -> when {
    rest.size != 3 -> usage(sender)
    rest[2] in listOf("default", "bowtie") -> find(sender, rest[1])?.let { update(sender, it, it.copy(style = rest[2])) }
    else -> Home.ITEMS.firstOrNull { it.equals(rest[2], true) }
        ?.let { material -> find(sender, rest[1])?.let { update(sender, it, it.copy(item = material)) } }
        ?: usage(sender)
}
```

补上分支之后，**补全列表也要一起补**（`default`/`bowtie` 之外还有 16 个物品名），
否则玩家还是得手打。

**怎么测才不会假绿**：断言的是**值变了**（`home.item == "BELL"`），不是「点下去没报错」。

## 51. ⚠️ 测试自己和自己赛跑：倒计时长度 == 等待长度

**现象**：传送粒子的那条测试**偶发**失败：期望「取消后粒子不再增加」，实际多了一大片。

**根因**：`flush()` 走 **60 个 tick**，而那条测试的倒计时是 **3 秒 = 60 tick**。两者一样长，
于是**传送有可能在 flush 结束之前就完成了**——完成之后播的是「到达」动画，取消命令对已经结束的
传送没有任何用，粒子自然继续涨。

失败与否取决于**异步的扣费什么时候回来**，所以它时好时坏。

**修法**：让被测的等待**明确长于**测试的等待：

```kotlin
// 六秒，不是三秒：flush 是六十 tick，三秒的倒计时也正好是六十 tick
teleportHarness(..., countdown = 6) { ... }
```

**怎么测才不会假绿**：凡是「在某段时间内取消」的测试，都要先看一眼**那段时间和测试自己的
等待是不是同一个数**。同一个数就意味着在赛跑。

## 52. ⚠️ 根命令没在 `plugin.yml` 里声明：菜单格子静悄悄执行成「未知指令」

**现象**：总菜单里的「幻翼」和「体型」两格点了没反应，聊天里也没有任何提示。

**根因**：两件事都做到了，**第三件没做**——

| 需要的东西 | 做了什么 |
| --- | --- |
| 路由注册 | `host.commands.register("phantom", id, …)` ✓ |
| `MeowoRuntime.aliases` 里有这个名字 | `"phantom" to listOf("phantom")` ✓ |
| **`plugin.yml` 里声明这个命令** | ✗ |

`plugin.yml` 里没有 `phantom` 的声明，Bukkit 就**根本没有这个命令**。`/meowo phantom` 走的是
`meowo` 的子路由，能用；但 `/phantom`（以及任何别的东西去调 `phantom` 这个命令）会落到 Bukkit 的
「未知命令」分支——**没有异常，没有日志，只有玩家眼里的「未知指令」**。

更糟的是菜单格子：格子的动作是 `meowo phantom`，本来是对的，但玩家看到的就是「点了没反应」。
**一个静悄悄失败的按钮，比一个报错的按钮难查得多。**

**为什么容易漏**：`plugin.yml` 的声明是**手写**的，路由是**代码里注册**的，两者没有一处会互相校验。
而 `MeowoRuntime` 里本来就有一段注释写着「**每一个**在 `plugin.yml` 里声明的命令都必须出现在
`aliases` 里」——那是**另一个方向**的检查（声明了但没路由），漏掉了**这一边**（有路由但没声明）。

**修法**：两处都要写，而且要有一道检查把它们绑在一起。

```yaml
# plugin.yml
commands:
  phantom:
    description: 免除原版的失眠幻翼
    usage: /phantom [on|off]
    permission: meowo.phantom
  size:
    description: 调整自己的体型
    usage: /size [up|down|reset|倍数]
    permission: meowo.size
```

```kotlin
// MeowoRuntime
"phantom" to listOf("phantom"), "size" to listOf("size"))
```

**怎么测才不会假绿**：光测「路由存在」不够——那测的是**注册**。要测**声明**：从 `plugin.yml` 里读出
`commands` 的键，和 `aliases` 的键、以及每个路由的 `permission` 三者对齐。少一个，运行时才会发现。

## 53. ⚠️ 菜单画的是「当时」的状态：点完不重画，界面像坏了

**现象**：总菜单里点一下「幻翼」，开关确实变了（聊天里有提示），但**格子上的字没变**——还是那一句
「会来找你」。玩家点了按钮，界面像没反应，于是又点一下。

**根因**：菜单格子画的是**打开那一刻**的快照。`UIAPI.open` 把 `overrides` 画进窗口，之后世界变了，
**没有人告诉那一屏**。TabooLib 的点击处理**不会**关掉窗口（`ClickListener.onClick` 只把物品锁住），
所以窗口一直开着，而那一屏的内容一直停在旧状态。

改状态的和画这一屏的是**两个 context**（`avatar` 画状态，`menu` 画格子），它们之间不许互相 import
（`verifyArchitecture` 会拦）。所以「状态变了」这件事必须**主动传过去**。

**修法**：事件总线（`api/event` 里的 `api.event` 事件就是干这个的）。

```kotlin
// api/event/Events.kt
data class AvatarChanged(val player: UUID)

// avatar context：状态一动就通知
host.events.publish(AvatarChanged(player.uniqueId))

// menu context：收到就重画自己那两格
host.events.subscribe(AvatarChanged::class.java) { event ->
    val player = Bukkit.getPlayer(event.player) ?: return@subscribe
    ui()?.refresh(event.player, SCREEN_MENU, avatarCells(player))
}
```

**`refresh` 而不是 `open`**：重开窗口会把界面从玩家手底下换掉（读作「闪了一下」）；
`UIAPI.refresh` 是**原地重绘**（`session.inventory.setItem`）。

**「玩家正看着这一屏吗」是 UI 模块的事**：`UIService.refresh` 先看 `renderer.openScreen(viewer)`，
不是这一屏就**什么都不做**。菜单模块不需要自己判断——它只管把自己那两格的内容交出去。

**怎么测才不会假绿**：断言的是**格子上的字变了**，不是「调用了 refresh」。而且要**真的点那一下**
（`FakeUI.click(slot)` → 派发指令 → 状态变 → 事件 → 重画），因为「重画」这件事只有走完整条链
才发生。只断言 `refresh` 被调用过，测的是 mock。

**怎么测才不会假绿**（真机那一半）：断言的是**格子上的字变了**，不是「调用了 refresh」。而且要
**真的点那一下**（`FakeUI.click(slot)` → 派发指令 → 状态变 → 事件 → 重画），因为「重画」这件事只有
走完整条链才发生。只断言 `refresh` 被调用过，测的是 mock。

真机上，菜单重画看得见的是**服务器有没有再发一包 `set_slot`**：客户端打开菜单（一次
`open_window`），然后改状态，服务器如果重画了那一格，就会再发一包 `set_slot`，而**窗口不会再开一次**。
「一次 open_window + 两次 set_slot」就是重画成功的证据；「两次 open_window」说明走的是重开而不是重画。

## 54. ⚠️ 「检查」和「扣减」之间有一个窗口：额度、冷却、计数都栽在这里

**现象**：单个玩家的每日额度在压力下会被超过；被队列拒绝的问题会把**后一次**问题的冷却戳一起带走；
风纪分被两次判定同时写入时只算一次。

**根因**：三处都是同一个形状——**先读、再判断、再写**，中间没有任何东西把它们绑在一起。

- `CallBudget.acquire` 先看 `mine.get() >= perPlayerCap`，再 `incrementAndGet()`：两个线程可以**同时**
  看见还有位置，然后**同时**拿走。额度被超过的数量，正好等于同时发问的线程数——而那正是额度唯一
  必须成立的那一刻。
- `lastAsked.remove(key)` 把**当时那一条**的戳和**后来那一条**的戳混为一谈：队列忙的时候第一条被拒，
  玩家在这中间又问了一次，第二次的戳被第一次的清理一起删掉——**玩家刚问完就被放行**。
- `RiskRegistry` 的 `Entry.value` 是一个普通 `var`，读改写不是原子的：两次判定同时到达时少算一次。

**修法**：**一把锁 + 只撤自己的戳**。

```kotlin
// 额度：检查和扣减在同一把锁里
fun acquire(lane: Lane, player: UUID): Boolean = synchronized(lock) {
    val mine = perPlayer[player] ?: 0
    if (mine >= perPlayerCap) return false
    if (!roomLocked(lane)) return false
    perPlayer[player] = mine + 1
    when (lane) { Lane.PROACTIVE -> proactiveUsed++; Lane.QUESTION -> questionUsed++ }
    true
}

// 冷却：只有戳还是自己的时候才撤（`remove(key, value)`，不是 `remove(key)`）
fun release(key: ConversationKey, at: Long): Boolean = stamps.remove(key, at)
```

**额度还多了一条规矩**：**退出不归还额度**。额度是**每日**额度，不是本次会话的额度；退出时把计数删掉，
等于给「断线重连」发了一张不限次数的通行证。

**通用结论**：任何「读出来 → 判断 → 写回去」的组合，都要问一句「**中间会不会有第二个人**」。
会，就上锁；不会，也写下来——下一个人会照着这个形状再写一遍。

## 55. ⚠️ 唯一的键空间：只与内存去重 + `INSERT OR REPLACE` = 旧消息被销毁

**现象**：某个 `#k3f9` 指向了别人的聊天记录；再刷新一次，那条记录又变成了另一段话。

**根因**：两件事凑在一起。

- **去重只看内存**：`MessageCode.generate(log.liveCodes())` 只跟**内存里那几千行**比对，而聊天日志
  在磁盘上保留着**几周**。所以新铸的码可以撞上一条**早就写进去**的行。
- **`INSERT OR REPLACE`**：撞上码的那一行会被**删掉**，再写进新的那一行。于是旧消息**永久消失**，
  而读者的 `#k3f9` 指向了新的那段对话。

**修法**：**码空间是有限的，所以它必须被完整地记账**。

36⁴ = 1 679 616 个码——小到可以用**位图**记（210 kB，一个 bit 一个码），不必存字符串集合。

- `CodeBook` 用一个 `BitSet` 记下所有用过的码：开局时把**磁盘上已有的码**读进来，之后每铸一个就占一个。
- `INSERT` 永远是**普通插入**：撞了就**失败**，失败会进日志，**没有任何东西被销毁**。唯一性由构造保证，
  拒绝只是最后一道背书。

**怎么测才不会假绿**：不要测「码看起来是随机的」。要测**它不与已存在的行相撞**，
以及**撞上时旧行还在**（`assertThrows` + 旧内容仍在）。

**通用结论**：`PRIMARY KEY` 上的 `INSERT OR REPLACE` 不是「幂等」，是「**删掉旧的写新的**」。
要幂等就写 `ON CONFLICT DO UPDATE`，要保留就写普通 `INSERT`。

## 56. ⚠️ 聊天路径上的一次数据库读

**现象**：聊天偶发地「顿一下」；人一多，延迟会叠起来。

**根因**：`ProfileTracker.onMessage` 里第一次见到某个玩家时，会去数据库读他**上一轮**的画像，
好把计数接上——而这条读**就在聊天路径上**（`ChatMessagePublished` 是聊天 context 的异步线程发的）。
一次 SQLite 读是几毫秒到几十毫秒，**乘以人数**就是可观的卡顿。

**修法**：**读还在，但不在那条路上**。

- 读被挪到 tracker **自己的线程**（一个 daemon 线程），读出来的结果叫 **base**：本次会话开始时那一行。
- 写的时候**把 base 和本次会话的计数合并**，于是那一行仍然是**一生**的总数，而不是本次会话的。
- 提示词看到的是同一份合并结果，所以「我们认识这个人多久了」没有变。

**通用结论**：**「接上上一轮」这类需求看上去像初始化，其实是 IO。**
初始化可以放在热路径上，IO 不行——热路径上的 IO 是把一个人的延迟乘以所有人的消息条数。

## 57. ⚠️ 玩家死了，命令会被服务器悄悄丢掉

**现象**：机器人连上服务器发 `/stop`，服务器**完全没反应**，只回一句红色的
`Chat disabled in client options`（客户端选项里聊天已禁用）。看起来像是权限问题，
其实既不是权限，也不是聊天设置。

**根因**：Paper 收命令前先看 `player.isRemoved()`：

```java
// ServerGamePacketListenerImpl#tryHandleChat
if (player.isRemoved() || (!isCommand && player.getChatVisibility() == HIDDEN)) {
    send(new ClientboundSystemChatPacket(translatable("chat.disabled.options"), false));
}
```

玩家**一旦死亡**（实体被移除），在重生之前所有命令都会被这条消息顶掉——**命令没执行**，
但客户端看起来像是「命令被拒绝了」。这台测试服 spawn 点旁边刷史莱姆，bot 落地 6 秒内就被打死，
于是 `/stop` 永远送不到。

**修法**：机器人**每轮都先发一次重生指令**（`client_command`，`actionId = 0`），再发命令；
命令本身还要**重复发**，保证有一次落在玩家活着的时候。

**通用结论**：`isRemoved()` 这种「实体还在不在」的状态会**拦截一切面向玩家的入口**，
不只拦截命令。调试「命令没反应」时，先确认玩家是不是死了，而不是先怀疑权限。
另外 Paper 会**把玩家没有权限的命令从 Brigadier 树里藏起来**，回一句
`Unknown or incomplete command`——所以「命令不存在」和「命令被隐藏」在客户端长得一模一样。
