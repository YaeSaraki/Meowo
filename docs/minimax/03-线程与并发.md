# 03 · 线程与并发

项目只有**三个执行域**。绝大多数并发 bug 都源于「在这三个地方搞混了」。本文给出允许矩阵。

---

## 1. 三个执行域

| 执行域 | 身份 | 能做什么 |
|---|---|---|
| **主线程** | Bukkit tick 线程 | 一切 Bukkit 对象：`Player`、`World`、`Inventory`、`Bukkit.getScheduler`、事件监听器 |
| **经济工作线程** | `ThreadPoolExecutor`，单线程，名字 `Meowo-Economy`（daemon） | 一切 JDBC / `Money` / 领域计算 / 事件发布 |
| **事件发布线程** | 发起 `publish` 的那个线程 | 执行订阅者回调——**不是**独立线程 |

事件总线**不引入第四个域**。README 明确拒绝过一个行为不确定的全局 `AsyncEventBus`：
「线程模型属于应用和平台边界，不另设一个行为不确定的全局 AsyncEventBus」。

### 允许矩阵

| 操作 | 主线程 | 经济线程 |
|---|---|---|
| 读 `Player` / `World` / `Inventory` | ✅ | ❌ **绝对不行** |
| JDBC / SQLite | ❌ 阻塞 tick | ✅ |
| `Money` 计算 | ✅（无状态值对象） | ✅ |
| 发 `BalanceChanged` | ⚠️ 会跑在主线程，订阅者须知 | ✅ 正常路径 |
| `Bukkit.getPlayer(uuid)` | ✅ | ❌ |
| `Bukkit.getServicesManager().load` | ✅（economy 关闭时返回 null） | — |

**硬性禁令**：命令绝不在 tick 线程执行 JDBC。这就是 `EconomyAPI` 全部方法都返回
`CompletionStage<BigDecimal>` 的原因——它不是「为了异步好看」，是**为了禁止在 tick 上做阻塞 IO**。

## 2. `EventBus` 精确语义

实现：`shared/src/main/kotlin/com/meowo/shared/event/EventBus.kt`（42 行，读完就够）。要点：

| 特性 | 行为 | 行号 |
|---|---|---|
| 匹配方式 | **精确类型**：`entry.type == event.javaClass` | `:29` |
| 执行顺序 | 订阅顺序，同步 | `:28` |
| 异常隔离 | 每个订阅者单独 try/catch，失败只调 `onFailure`，不影响其他订阅者 | `:30-35` |
| 嵌套发布 | 允许，**立即分发**（不是排队） | — |
| 退订 | `AutoCloseable`，退订会等当前回调结束并阻止未来投递 | `:23` |
| 并发发布 | `ReentrantLock` 串行化 | `:26` |
| 关闭后发布 | **no-op，不抛异常** | `:27` |
| 关闭后订阅 | `check(!closed)` 抛 `IllegalStateException` | `:20` |

**两个容易踩的点**：

1. **精确类型匹配**——发 `BalanceChanged` 不会投递给 `Object` 的订阅者，
   发子类也不会投递给父类订阅者。事件类型设计要精确，不要指望继承层次。
2. **关闭后发布是 no-op 而非异常**——这是刻意的。关闭竞态下（事务已提交，
   事件还没发，进程正在关停），抛异常会把**已提交成功的支付**报成失败。
   宁可丢一条通知，也不能把成功报成失败。见 [01 §5](01-架构红线.md)。

**回调运行在发布线程**。所以订阅者如果做耗时操作，就会拖慢发布者（可能是主线程）。
跨进程/耗时任务不要放回调里；需要 Bukkit 就 `host.mainThread`。

## 3. 经济工作线程

`EconomyApplicationService`（`contexts/meowo-economy/src/main/kotlin/.../EconomyApplicationService.kt:24-35`）：

```kotlin
ThreadPoolExecutor(
    1, 1,                       // 单线程 —— 保证提交顺序 = 执行顺序
    0, TimeUnit.MILLISECONDS,
    ArrayBlockingQueue(1024),   // 有界
    ThreadFactory { Thread(it, "Meowo-Economy").apply { isDaemon = true } },
    AbortPolicy()               // 队列满 → 抛 RejectedExecutionException
)
```

**为什么单线程**：`reserve` → `settle` 这类操作必须**按提交顺序**执行。
teleport 关闭时连发 `cancelTeleport`，多线程会乱序。

**为什么有界 + Abort**：队列满时立刻失败，返回 `EconomyException(UNAVAILABLE)`，
而不是无限堆积把内存吃光。`UNAVAILABLE` 有对应语言键 `error-unavailable`。

```kotlin
internal fun <T> submit(action: () -> T): CompletableFuture<T> = try {
    CompletableFuture.supplyAsync(action, worker)
} catch (_: RejectedExecutionException) {
    CompletableFuture.failedFuture(EconomyException(EconomyError.UNAVAILABLE))
}
```

注意是 **exceptional completion** 而非抛异常：调用方统一走 `whenComplete` 就能处理。

**`SettlementApplicationService` 共用这个 worker 和同一个 SQLite 连接**（`worker.submit { ... }`）。
所以 economy 内部所有操作天然串行，`@Synchronized` 是双保险。

## 4. 提交后发事件

```kotlin
private fun change(player: UUID, amount: BigDecimal, operation: Operation) = submit {
    val tx = domain.change(player, operation, Money.of(amount))   // 1. 事务提交在这里完成
    events.publish(BalanceChanged(tx.id, player, tx.before.decimal(), tx.after.decimal(), operation.name))  // 2. 提交后才通知
    tx.after.decimal()                                            // 3. 返回操作后余额
}
```

`publish` 在工作线程上**同步**执行订阅者。所以 `BalanceChanged` 订阅者也在经济线程上跑——
menu 的订阅者因此必须 `host.mainThread(...)` 才能碰 `Inventory`（它确实这么做了）。

`Settlement<T>` 的 `changes` 列表是「这次事务改了哪些钱包」的权威来源，
`SettlementApplicationService.publish` 遍历它逐条发 `BalanceChanged`——
所以**一次转账会发两条事件**（一条 PAY_SENT、一条 PAY_RECEIVED）。

## 5. 两个回主线程的模式

### `host.mainThread(active) { ... }`

`platform/src/main/kotlin/com/meowo/platform/PlatformHost.kt`：

```kotlin
fun mainThread(active: () -> Boolean = { true }, action: () -> Unit) {
    if (!plugin.isEnabled) return
    if (Bukkit.isPrimaryThread()) { if (active()) action(); return }   // 已在主线程 → 直接跑
    try { Bukkit.getScheduler().runTask(plugin, Runnable { if (plugin.isEnabled && active()) action() }) }
    catch (e: IllegalPluginAccessException) { if (plugin.isEnabled) throw e }   // 插件正在停用
}
```

三重保护：插件是否启用、**context 是否还启用**（`active`）、停用竞态的异常处理。

`active` 由 context 传入自己的 `active::get`。**context 关闭后，所有已排队的回调静默丢弃**。

### `host.reply(sender, future, active) { success }`

统一处理异步命令的**成功**和**失败**，含错误本地化：

```kotlin
future.whenComplete { value, failure ->
    if (failure != null) {
        val cause = if (failure is CompletionException) failure.cause ?: failure else failure  // 拆 CompletionException
        if (cause !is EconomyException) plugin.logger.log(SEVERE, "Economy operation failed", cause)  // 业务错误不刷堆栈
        mainThread(active) {
            if (sender !is Player || sender.isOnline)
                messages.send(sender, if (cause is EconomyException) "error-${cause.code.name.lowercase()}" else "internal-error")
        }
    } else mainThread(active) { if (sender !is Player || sender.isOnline) success(value) }
}
```

三条要点：
1. **`CompletionException` 必须拆包**，否则 `cause is EconomyException` 永远 false，
   所有业务错误都会变成 `internal-error` 且刷 SEVERE 堆栈。
2. **业务错误不记堆栈**（`EconomyError` 是预期内的），存储错误才记。
3. **`sender !is Player || sender.isOnline`** —— 控制台无 `isOnline`，玩家可能已下线。

**新写异步命令一律用 `host.reply`**，不要手写 `whenComplete`——否则错误文案和日志策略会不一致。

## 6. 传送的三段式线程边界

`teleport` 是本项目最复杂的并发场景（`contexts/meowo-teleport/.../TeleportContext.kt:89-111`）：

```
[主线程]  accept
   │
   ├─ flights[ticket] = request              ← 占位：防止重复结算
   ├─ economy.reserveTeleport(...)           ← 提交到经济线程
   └─ whenComplete {                        ← 经济线程回调
        └─ host.mainThread {                 ← 切回主线程
             检查 source/target 在线、存活
             move(source, target)            ← 主线程，同步移动
             economy.settleTeleport(ticket, moved)   ← 提交回经济线程
             flights.remove(ticket)
        }
   }
```

**关键不变量**（`TeleportContext.kt:101` 注释）：
> Movement is synchronous on the main thread; close/quit cannot interleave before settlement is queued.

`move` 在主线程同步完成后，**紧接着**就 `settle` 入队。
`quit` / `close` 事件也是主线程，无法在两者之间插入。所以**移动成功和结算入队之间不会漏退款**。

**残留风险（已接受）**：如果进程恰好在「世界移动成功后、税收提交前」崩溃，
重启时 `recoverPending()` 会当作失败退款——玩家白传送一次，但**不会重复扣款**。
世界移动和 SQLite 无法组成同一原子事务，见 teleport README。

`flights` map 是防重复结算的守卫：`if (flights[request.ticket] == null) return@mainThread`。

**测试手法**：把移动动作作为构造参数注入，测试里换成 lambda 计数：

```kotlin
TeleportContext(host, TeleportSettings(5, particles), move = { a, b -> moved++; true })
```

见 `MeowoRuntimeTest.teleportHarness`（`MeowoRuntimeTest.kt:181-190`）。

## 7. 关闭时的排空

```kotlin
override fun close() {
    worker.shutdown()                                    // 不再接受新任务
    check(worker.awaitTermination(30, TimeUnit.SECONDS)) // 最多等 30s
    // 正常：terminated() 回调里 onStopped() → repo.close()
    // 超时：抛异常记录，但工作线程继续排空，terminated() 最终仍会关连接
}
```

`onStopped` 是构造时传入的 `repo::close`（`EconomyContext.kt:28`），
挂在 `ThreadPoolExecutor.terminated()` 覆写上——**只在真正排空后才关 JDBC**。

**绝不在任务执行中强行关连接。** 这是 `EconomyContext.close()` 里
「先 `service.close()`，只有 service 为 null 才 `repo?.close()`」的原因。

## 8. 并发改动自查

- [ ] 新增的 Bukkit 访问都在主线程（或经 `host.mainThread`）
- [ ] 新增的 DB 访问都在 `worker.submit {}` 里
- [ ] 异步回调用 `host.reply(...)` / `host.mainThread(active::get) { ... }`
- [ ] 新 context 实现了 `active` 闸门并在 `close()` 里先置 false
- [ ] 依赖执行顺序的操作依赖**单线程** worker，不要引入并行提交
- [ ] 事件订阅者如果碰 Bukkit，必须 `host.mainThread`
- [ ] 新错误码有对应的 `error-<code>` 语言键（否则显示原始键名，见 [08 §2](08-坑与反模式.md)）
