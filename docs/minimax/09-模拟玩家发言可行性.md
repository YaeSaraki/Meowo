# 09 · 发言者名字（方案 A；方案 B 已废弃）

> **状态：方案 A。** 全部玩家可见的聊天消息仍以「发言者」形式呈现，命名规则 `XxxCat`（`Xxx` 恰好 4 字符）。
> 实施位置：`platform/Messages.kt` + `platform/ChatLine.kt`；名字在语言文件的 `speaker-*` 键，可自行改名。
>
> **曾经采用过方案 B（`ChatType.CHAT.bind`），因为它能白拿原版的 `<名字> 消息` 格式而放弃了。
> 那对尖括号是客户端画的，服务端删不掉。** 下面是完整经过，别再走回去。

实现核心只有一行：

```kotlin
player.sendMessage(ChatLine.say(name, message))
```

名字和正文都由我们自己拼好，整行作为一条普通消息发出去。**不涉及 NMS**。

## 0. 实施后的规则

| 项 | 约定 |
|---|---|
| 发言者 | `MeowCat`（系统/通用）、`EconCat`、`MenuCat`、`RendCat`、`WarpCat`、`SitCat`、`HatCat`、`IdleCat`、`MineCat`、`TeleCat`、`ShadCat`、`NestCat` |
| 改名 | 语言文件 `speaker-<id>` 键；留空或删掉则回落到代码里的默认值 |
| 未知 id | 回落到 `UnknownCat`，**绝不会显示原始键名** |
| 解析顺序 | 精确键 → 键前缀 → `system`（见 `Messages.SPEAKER_KEYS` / `SPEAKER_PREFIXES`） |
| 玩家 | 一条普通聊天消息，`\n` 保留在内容里（不拆成多条） |
| 控制台 / RCON | **不带发言者**，去色后按行拆分 |
| 菜单标题 / 物品名 | **不套发言者**，`menu-*` 走 `text()` 而非 `send()` |

> **为什么玩家只发一条而控制台按行拆**：发言者前缀属于「这条消息」，
> 逐行重复会让 `/meowo help` 出现十几个 `MeowCat`。控制台没有发言者概念，按行拆更易读。
> 注意：**聊天消息内嵌换行的客户端渲染效果尚未实机验证**，见 §5。

当前各发言者负责的键数（实测 zh_CN 全量 662 键，与 `Messages.SPEAKER_KEYS` / `SPEAKER_PREFIXES` 一致）：

> `agents-*` 落在兜底里是**故意的**：那些键是猫的拒绝句，由猫自己的 `speakerId` 署名，走 chat context 的
> 私聊渲染，**不经过** `messages.send`，所以没有发言者归属可言。给它们安一个 owner 反而会造出一只
> 不存在的猫。

> 全部 `menu-*` 都落到 `MeowCat`——而那三条精确键指向的键**根本没人发送**。现在改成一条
> `menu-` 前缀，规则说一次而不是列今天恰好存在的键；`unavailable` 共享键已拆成
> `shop-unavailable` / `home-unavailable` / `menu-unavailable` 三条，各归各的猫。

> 落到 `MeowCat`，且 `speaker-spawn` 配置永远读不到。已修复并加测试锁定归属。
> 这正是下面「忘了加也不会崩，但归属会错」那条的真实案例。

## 1. 机制考古：`minecraft:chat` 的 sender 槽位

服务端 jar 里的 `data/minecraft/chat_type/chat.json`（本地实测，已从
`.run/server/versions/26.2/paper-26.2.jar` 提取）：

```json
{ "chat": { "parameters": ["sender", "content"], "translation_key": "chat.type.text" } }
```

`chat.type.text` 在**客户端**语言文件里是 `"<%s> %s"`，两个占位依次是 **sender** 和 **content**。

> ⚠️ 关键：这两个字面量只存在于**客户端资源**。服务端从头到尾没写过这对尖括号。

Adventure 的接口签名（实测 `adventure-api 5.2.0`）：

```
net.kyori.adventure.chat.ChatType
  static final ChatType CHAT
  default ChatType$Bound bind(ComponentLike name)
  default ChatType$Bound bind(ComponentLike name, ComponentLike target)

net.kyori.adventure.chat.ChatType$Bound
  Component name()
  Component target()
```

也就是说 **`sender` 槽位由调用方通过 `bind(...)` 填入**，服务端可以自由指定**内容**——
但**不能指定格式**。格式写死在客户端。

Paper 官方文档给的就是这个用法（Signed message argument 示例）：

```java
target.sendMessage(msg, ChatType.CHAT.bind(context.getSource().getSender().name()));
```

## 2. 为什么放弃了方案 B

### 现象

玩家反馈所有消息都被 `<>` 包住，要求去掉。

### 排查结论：`<>` 不在我们这边

依次排除：

1. **语言包**——含 `<` 的 31 行全是 `#` 注释和 `/tpaccept <玩家>` 这类用法提示；
2. **代码**——没有任何一处拼接 `<%s>`；
3. **归一化**——`ChatPipeline.normalise` 里没有剔除 `<` 的逻辑（私信路径本来也不走它）。

真正的原因是**方案 B 本身**。`bind(name)` 把名字塞进 sender 槽位，客户端拿 `chat.type.text`
去渲染这个槽位，于是自己套上了 `<>`。服务端无论怎么改字符串都没用，因为那一步发生在
**组件已经发到线上之后**。

### 顺带发现的第二个 bug

`Messages.privateMessage` 把**整行**当成名字传进 `sayAs`，又把正文原样传了一遍：

```kotlin
sayAs(sender, ChatLine.private(from, to, delivered, body, quote, replyCommand), body)
//                                        ↑ 整行已经含 body                    ↑ 又来一次
```

于是一条私信在屏幕上长这样：`<✉ Alice → Steve ✔ 你在吗> 你在吗`——
括号里一遍、括号后一遍。这才是「被 `<>` 包裹」的观感来源。

### 修复

名字自己拼，整行自己发：

```kotlin
fun sayAs(sender: CommandSender, name: Component, message: Component) =
    deliver(sender, ChatLine.say(name, message))          // name + " " + message

private fun deliver(sender: CommandSender, message: Component) {
    if (sender is Player) sender.sendMessage(message)     // 不带 chat type
    else { /* 去色、按行拆、控制台老样子 */ }
}
```

丢掉 chat type **没有任何损失**：这些行从来就没有签名、没有真实 profile，
sender 槽位唯一买到的就是那个装饰——而那正是我们要摆脱的东西。

### 第二个来源：玩家公开聊天（第一轮没发现）

改完上面这些，玩家说**普通消息**还是 `<Steve> 你好`。因为 `chat.type.text` 有两个入口：

| 来源 | 谁在用 | 状态 |
|---|---|---|
| `Messages.sayAs` → `ChatType.CHAT.bind(name)` | 猫说话、私信、邮箱 | ✅ 上一步已去掉 |
| Paper 的 `ChatRenderer.defaultRenderer()` | **玩家公开聊天** | ❌ 当时还在用 |

`ChatContext.onChat` 一直**只改写 `event.message(...)`，没碰渲染器**，
所以事件里根本没有 `<>` 可删 —— 搜自己的代码永远搜不到。

修法是装一个自己的 `ChatRenderer`。决定性的分支在
`io.papermc.paper.adventure.ChatProcessor.complete()`（反编译实测）：

```java
key = (renderer instanceof ChatRenderer.Default) ? ChatType.CHAT : PAPER_RAW;
```

`ChatType.CHAT` 带装饰；`PAPER_RAW`（`paper:raw`）在 `ViewersOutgoingChat#adventure` 里
查不到于 `BUILT_IN_CHAT_TYPES`，于是走 `ChatType.chatType(Key)` 这个**单参重载**——
**没有装饰**。插件装的渲染器都不是 `ChatRenderer.Default`，所以一装就切过去。

⚠️ 渲染器要返回**完整的一行**，只返回正文的话客户端照样套 `<名字>`，变成 `<Steve> <正文>`：

```kotlin
event.renderer(ChatRenderer.viewerUnaware { source, displayName, body ->
    ChatLine.publicLine(displayName, service.profileCardFor(source.name), body)
})
```

> 同一个括号查了两轮。教训见 [08 §25b](08-坑与反模式.md)：**同一个效果往往有多个生产者**，
> 修掉一处不代表修完，挨个问「这条是谁画的」。

### 守门测试

`platform/NoChatTypeDecorationTest` 扫全部 `.kt` 源码，禁止再出现 `ChatType`。
单元测试抓不到这个坑：`ChatLine` 两种做法都拼得对，尖括号只在组件上线后才出现。
`ChatLineTest` 另外钉住「成行文本里不含 `<` `>`」「正文只出现一次」。

## 3. 三种方案（结论）

| 方案 | 做法 | 能否显示名字 | 代价 / 风险 | 结论 |
|---|---|---|---|---|
| **A. 自己拼前缀** | `ChatLine.say(name, body)` → `sendMessage` | 是（就是文字） | 无依赖、无 NMS | ✅ **采用**。格式完全自己说了算 |
| **B. `ChatType.CHAT.bind(name)`** | `player.sendMessage(c, ChatType.CHAT.bind(name))` | 是（真 sender 槽位） | ❌ **格式由客户端决定**，硬塞进 `<> ` | ❌ **已废弃**，见 §2 |
| **C. 假玩家 / NPC** | TabooLib NPC、ProtocolLib 假玩家 | 是，且是「真」玩家 | 重、依赖多、每版本都要维护 | ⚠️ 违背「轻量、不做过度工程」 |

选 A 的代价：B 能拿到的 sender 槽位语义，A 拿不到。实测下来**这不重要**——
按 [15-chat](15-chat.md) 的结论，这些提示本来就该长得像私信而不像真人发言。

## 4. 实施时的注意事项（已落实）

1. **只对玩家有效。** 控制台/RCON 没有聊天框也没有颜色，继续走 `Messages.deliver` 的去色纯文本路径。
2. **不要冒充真人。** 名字固定是虚构的 `XxxCat`，绝不 `bind` 一个**在线真人**的名字。
3. **与颜色体系正交。** 名字和正文都是 `Component`，`§` 走 `LegacyComponentSerializer`。
4. **名字可本地化。** `speaker-*` 是普通语言键，管理员可在自己的语言文件里改名。
5. **不要用 `Component.text` 装含 `§` 的文案**——会显示成字面量 `§a`，见 [08](08-坑与反模式.md)。

## 5. 尚未验证的部分

以下需要**真实客户端**才能确认，本地无法断言：

- **聊天消息内嵌 `\n`（如 `/meowo help` 的 14 行）是否被客户端渲染成换行**——
  若不换行，整段帮助会挤成一行。这是当前最需要实机确认的一项。
- 去掉 chat type 后，客户端是否还把这类消息按「系统消息」处理（例如静音开关是否仍能屏蔽）。
- 悬停 / 点击事件在普通聊天消息上的表现是否与之前一致。

结论中的「可行」指的是**服务端 API 层面成立**；「观感如何」必须实机验证。
