# 02 · 运行时与生命周期

启动、重载、关闭三张顺序表，以及 context 必须遵守的资源登记契约。

全部逻辑集中在两个文件：
- `core/src/main/kotlin/com/meowo/core/MeowoRuntime.kt`（组合根）
- `shared/src/main/kotlin/com/meowo/shared/lifecycle/Context.kt`（`Context` / `ContextManager`）

---

## 1. 启动顺序

`MeowoCore.onEnable` → `MeowoRuntime.start()`（`MeowoRuntime.kt:32-61`）：

```
1. saveDefaultConfig()
2. 读 config.yml → messages.load(locale, languageMode)    ← 语言先就位，后续所有文案可用
3. 注册 core 自己的路由：help / info / reload      ← routes 列表，独立于 context
4. 取 plugin.yml 的 meowo 命令，绑定 CommandRouter
5. 绑定别名 pay / tpa / tpaccept / tpdeny / tpacancel
   —— 每个别名把参数前缀拼回去再交给同一个 router
6. registerEvents(this)                            ← 唯一的 Bukkit Listener：PlayerJoinEvent → PlayerJoined
7. applySettings(initial)                          ← 真正启动 context
8. log "Meowo ready; contexts=[...]"
```

`MeowoCore` 自己不做任何业务，只做「构建 runtime → start → 失败则 close 并重抛」。

`applySettings` 内的 context 启用顺序是**硬编码的依赖顺序**（`MeowoRuntime.kt:75-78`）：

```
economy  →  menu  →  render  →  teleport  →  spawn
```

`economy` 必须最先（它注册 `SettlementAPI`），`teleport` 必须在 `economy` 之后
（`start()` 里 `requireNotNull(load(SettlementAPI))`，服务不存在直接失败）。
`spawn` 放最后：它免费、不依赖 economy，但**必须排在 economy 之后**——
它复用 `platform/SafeDestination` 与 `host.mainThread`，且反向停用时先于 economy。

**`start()` 失败不会污染其他 context**：`ContextManager.enable` 捕获异常 → 调 `context.close()`
回滚该 context 资源 → 记录 → 返回 false，循环继续。

## 2. 重载矩阵（`MeowoRuntime.kt:66-80`）

`/meowo reload` 的语义不是「全部重启」，而是**按需重启受影响的 context**。这段代码顺序敏感：

| 条件 | 动作 | 为什么 |
|---|---|---|
| 解析 `GlobalConfig` 抛异常 | 整体拒绝，保留运行中的所有模块，回复 `reload-failed` | 配置坏掉不该弄停服务 |
| `teleport` 设置变化 **或** `economy` 被关闭 | `disable("teleport")` | **必须先停 teleport**，让已接受的预扣款能退款 |
| `locale` / `language-mode` 变化 **或** `currency` 变化 | `disable("menu")` | 旧标题和已发出的异步回复不能跨越语言切换 |
| `renderLimit` 变化 | `disable("render")` | 上限变了要重算，新实例才带新 limit |
| `spawn` 设置变化 | `disable("spawn")` | 预热/冷却/安全扫描参数在 `start()` 时读取，新实例才带新值 |
| 不在 `next.contexts` 里的 | 逆序 `disable` | 保持停用依赖顺序 |
| 需要且未启用 | 按 economy→menu→render→teleport→spawn `enable` | 见上 |

成功与否的判定（`MeowoRuntime.kt:45`）：

```kotlin
val expected = if ("economy" in next.contexts) next.contexts else next.contexts - "teleport"
// contexts.ids() == expected  →  reloaded
// 否则                          →  reload-partial（提示去查日志和 /meowo info）
```

`teleport` 依赖 `economy`，所以 economy 关掉时 teleport 不算「部分失败」。
若 economy 开着但 teleport 启动失败（少见），会报 `reload-partial`。

**`info` 永远显示实际状态**（`contexts.ids()`），不显示配置期望值。这是排障时唯一可信的来源。

## 3. 关闭顺序

`MeowoRuntime.close()`（`MeowoRuntime.kt:82-88`）：

```
1. HandlerList.unregisterAll(this)   ← core 自己的 PlayerJoinEvent 监听
2. contexts.close()                   ← 逆序：spawn → teleport → render → menu → economy
3. events.close()                     ← 总线关闭，此后 publish 变 no-op
4. routes 逆序关闭                     ← help/info/reload
5. 所有命令 setExecutor(null) / tabCompleter = null
```

`ContextManager.close()`（`Context.kt:27`）是 `active.keys.toList().asReversed().forEach(::disable)`，
`active` 是 `LinkedHashMap`（保持启用顺序），所以逆序 = **spawn/teleport 先停、economy 最后停**。

这个顺序是**退款能落地的前提**：

```
teleport.close()   →  把所有在途请求 cancelTeleport()，任务进入经济队列
economy.close()    →  排空队列（最多 30s）→ 队列真正终止 → JDBC 关闭
```

**顺序反了会怎样**：economy 先关连接，teleport 的退款任务随后执行就会在已关闭的连接上失败，
玩家钱被吞。所以不要改这个顺序，也不要在 `ContextManager` 里加「按 id 排序」之类看似聪明的逻辑。

## 4. `Context` 契约

```kotlin
interface Context : AutoCloseable {
    val id: String
    fun start()
}
```

实现必须遵守：

- **`close()` 必须幂等。** `ContextManager` 在启动失败时会先 `close()` 回滚，之后 reload 又会再关一次。
- **`id` 必须与配置开关名一致。** 门禁、reload 判定、`info` 输出都靠它。
- **`start()` 抛异常 = 整个 context 启动失败**，必须自洽：要么成功到能服务，要么能被 `close()` 干净回滚。
- **所有可关闭资源登记到 `resources` 列表**，`close()` 时逆序释放：

```kotlin
private val resources = mutableListOf<AutoCloseable>()

override fun start() {
    active.set(true)
    Bukkit.getPluginManager().registerEvents(this, host.plugin)
    resources += AutoCloseable { HandlerList.unregisterAll(this) }   // 先登记，后续出错也能回滚
    resources += host.commands.register("menu", object : Route { ... })
    resources += host.events.subscribe(BalanceChanged::class.java) { ... }
}

override fun close() {
    active.set(false)                                   // 先关闸：后续 mainThread 回调直接被吞
    resources.asReversed().forEach { it.close() }        // 逆序：订阅 → 命令 → 监听器
    resources.clear()
    // 最后才是 context 独有的收尾（如关库存、关服务）
}
```

**`active` 闸门的意义**：`host.mainThread(active::get)` / `host.reply(..., active::get)` 里的
`active` 是「这个 context 还开着吗」。关停瞬间可能有已排队的异步回调要回主线程，
`active` 让它们变成 no-op，而不是对着已释放的状态操作。见 [03](03-线程与并发.md)。

**登记顺序 = 释放逆序**。事件订阅要放在监听器之后登记吗？不必刻意，但要让
「先设 `active=false`，再释放资源」这个顺序稳定成立——前者防竞态，后者防泄漏。

## 5. 服务注册与注销

对外能力走 **Bukkit ServicesManager**，不用全局 `lateinit`（`README.md:131` 的理由：避免不可撤销的全局单例）：

```kotlin
Bukkit.getServicesManager().register(SettlementAPI::class.java, settlements, host.plugin, ServicePriority.Normal)
resources += AutoCloseable { Bukkit.getServicesManager().unregister(SettlementAPI::class.java, settlements) }
```

`unregister` 的第二个参数必须是**注册时那个确切实例**，不能新建一个。

**模块重载后旧引用会拒绝新请求**（worker 已 shutdown → `submit` 抛 `RejectedExecutionException`
→ 转成 `EconomyException(UNAVAILABLE)`）。所以调用方要**在每次使用时重新 `load`**，
不要缓存 API 引用。`MenuContext.refresh` 正是每次都 `load(EconomyAPI::class.java)`。

## 6. economy 的两个特殊时序

### 恢复先于一切（`EconomyContext.kt:30-32`）

```kotlin
val settlements = SettlementApplicationService(...)
// Recovery is queued first, before any wallet, command or login operation.
settlements.recover().whenComplete { ... }
```

`recover()` 把所有 `PENDING` 传送托管退款，**排在队列最前面**。
必须这样：若一个玩家在上一进程崩溃时留了 PENDING 预扣，
后续任何对同一钱包的操作都应在退款之后才跑，否则 `pending()` 预留额度算错。

### 关闭时先撤销入口，再排空（`EconomyContext.kt:50-58`）

```kotlin
active.set(false)
resources.asReversed().forEach { it.close() }   // 先退订、注销服务、撤路由
service?.close()                                 // 再排空 worker（30s）
```

`service.close()` 内部：`shutdown()` → `awaitTermination(30s)`。
- 正常排空：`terminated()` 回调关 JDBC。
- **超时**：抛异常记录失败，但**工作线程继续排空**，`terminated()` 最终仍会关连接。
  绝不在任务执行中强行关连接。

## 7. 停用语义矩阵

| 动作 | economy | menu | render | teleport | spawn |
|---|---|---|---|---|---|
| 单独停用 | 撤销服务 + 排空队列关库 | 关闭已打开的库存 | 销毁所有假实体 | 清理请求、退款、停粒子 | 取消预热与冷却表 |
| 停 economy 的连带影响 | — | 仍可运行，`refresh` 显示「经济模块未启用」 | 无影响 | **自动停用**（`applySettings` 先关它） | 无影响（免费，不依赖 economy） |
| 停 menu | 无影响 | — | 无影响 | 无影响 | 无影响 |
| 停 render | 无影响 | 无影响 | — | 无影响 | 无影响 |
| 启动失败的影响面 | 自己 | 自己 | 自己（仅缺 PacketEvents 时） | 自己 | 自己 |
| 重载关闭触发条件 | 不在配置 | locale / language-mode / currency 变 | limit 变 | teleport 设置变或 economy 关 | spawn 设置变 |

> **`spawn` 不依赖 economy**，所以停 economy 不会连带停它——这与 teleport 不同。
> 但它仍排在 economy 之后启用，纯粹是为了让依赖顺序保持单向可读。

**菜单关闭必须关库存**（`MenuContext.close()` 末尾遍历 `getOnlinePlayers()` 调 `closeInventory()`），
否则玩家手里留一个点不动的空容器。
