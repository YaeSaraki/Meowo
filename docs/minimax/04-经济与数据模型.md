## 1. `Money`：整数分值对象

`contexts/meowo-economy/domain/src/main/kotlin/com/meowo/economy/domain/model/Money.kt`

```kotlin
@JvmInline
value class Money private constructor(val minor: Long)      // 单位：分
```

| 常量 | 值 |
|---|---|
| `MAX_MINOR` | `999_999_999_999_99L` = 999999999999.99 |
| `ZERO` | `Money(0)` |

**四个拒绝规则**（都抛 `EconomyException(EconomyError.INVALID_AMOUNT)`）：

1. **负数** — `fromMinor` 校验 `value < 0`
2. **超上限** — `fromMinor` 校验 `value > MAX_MINOR`
3. **多余小数** — `of()` 用 `setScale(2, RoundingMode.UNNECESSARY)`，多余有效位抛 `ArithmeticException`
4. **溢出** — `plus` 先判 `other.minor > MAX_MINOR - minor` 再相加；`of()` 用 `longValueExact()`

**不做隐式四舍五入。** `Money.of(BigDecimal("0.001"))` 直接抛错，不是变成 0.00。

运算语义：
- `plus` 溢出 → `LIMIT_EXCEEDED`（不是 `INVALID_AMOUNT`，可区分）
- `minus` 余额不足 → `INSUFFICIENT_FUNDS`（**领域层就拒绝透支**，不需要在命令层再判）

跨边界统一转 `BigDecimal`：`decimal()` = `BigDecimal.valueOf(minor, 2)`，反向 `of()`。

## 2. 数据库

文件：`plugins/Meowo/economy/wallets.db`（真服默认；测试用 `@TempDir`）。
连接参数（`SqliteWalletRepository.kt:19-23`）：

```kotlin
DriverManager.getConnection("jdbc:sqlite:$absolutePath")
PRAGMA journal_mode=WAL
PRAGMA busy_timeout=5000
```

**表结构（8 张，`SqliteWalletRepository.kt:24-33`）**。金额一律 `INTEGER` 分。

| 表 | 主键 | 作用 | 关键约束 |
|---|---|---|---|
| `wallets` | `player` | 余额 | `CHECK(balance >= 0 AND balance <= MAX)` |
| `transactions` | `id` | 每笔钱包变动流水 | 索引 `transactions_player(player)` |
| `transfers` | `id` | 转账双方与金额 | `CHECK(amount > 0)` |
| `teleport_charges` | `id` | 传送费托管 | `CHECK(state IN ('PENDING','COMMITTED','REFUNDED'))` |
| `eco_treasury` | `id=1` | eco 税收池 | 单行，`CHECK(balance >= 0 AND ...)` |
| `eco_ledger` | `reference` | 池子进出流水 | `delta` 有正有负；`reason` = `TP_TAX` / `DAILY_SUBSIDY` |
| `daily_claims` | `(player, day)` | 每日领取去重 | 复合主键，**天然幂等** |

**两个半唯一索引/唯一约束是幂等性的基石**：

```sql
CREATE UNIQUE INDEX teleport_pending_player ON teleport_charges(player) WHERE state='PENDING'
CREATE PRIMARY KEY daily_claims(player, day)
```

前者保证**一个玩家同时只能有一笔在途传送费**；
后者保证重连、重载、重启、并发连接都不会重复领取补助。

### 升级约定

**服务升级只新增表/索引，保留已有钱包**（economy README 明确要求）。
所有 DDL 都是 `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`，
`eco_treasury` 用 `INSERT OR IGNORE` 播种。因此**不要写会破坏旧钱包的迁移**。

## 3. 事务边界

所有写操作包在 `atomic {}`（`SqliteWalletRepository.kt:44-54`）：

```kotlin
connection.createStatement().use { it.execute("BEGIN IMMEDIATE") }
try { val value = action(); ...COMMIT; return value }
catch (e: Exception) { try { ...ROLLBACK } catch (rollback: Exception) { e.addSuppressed(rollback) }; throw e }
```

**`BEGIN IMMEDIATE`（不是 DEFERRED）**：立刻取写锁，避免两笔转账先读后写导致丢失更新。

- **余额变更与流水写入必须在同一事务**：`write()`（`:60-68`）先更新 `wallets`，
  再插入 `transactions`，同事务。任一失败整体回滚。
- `check(execute("UPDATE wallets ...") == 1)` —— 影响行数不是 1 说明钱包行丢了，属于不可能状态，直接抛。
- 方法上的 `@Synchronized` 是双保险（单线程 worker 已保证串行）。

## 4. 传送费托管状态机

```
                    reserve(ticket, player, policy)
                              │
                              ▼
                     ┌─────────────────┐
                     │     PENDING     │  已从钱包扣款，暂存在 teleport_charges
                     └─────────────────┘
                       │              │
        settle(success=true)   settle(success=false) / cancel
                       │              │
              ┌────────▼───┐   ┌──────▼──────┐
              │ COMMITTED  │   │  REFUNDED   │
              │ 入税收池   │   │  退回钱包   │
              └────────────┘   └─────────────┘
```

**幂等**：`settleInside`（`:101-116`）开头

```kotlin
if (old.state != ChargeState.PENDING) return Settlement(old)   // 已终态 → 原样返回
```

所以**重复结算、重复取消、崩溃后恢复都安全**。`reserve` 也幂等：
同 `ticket` 再来直接返回原记录（`:88`）。

- **COMMITTED 才入池一次**：写 `eco_treasury` + `eco_ledger(reason='TP_TAX', reference=ticket)`，
  `reference` 是主键，天然去重。
- **REFUNDED 只退一次**：`write(wallet, wallet.balance + fee, Operation.TP_REFUND)`。
- **启动恢复**：`recoverPending()`（`:120-123`）把所有 PENDING 当失败退款，
  在 `EconomyContext.start()` 里**第一个入队**（见 [02 §6](02-运行时与生命周期.md)）。

## 4b. 传送的接受时序与垫付

接受流程严格按此顺序，**顺序本身就是契约**：

```
请求 ──▶ 对方同意（命令或点击聊天操作）
          │   ← 此时还没有扣任何钱
          ▼
      reserveTeleport(ticket, 付款人)      ← 钱进入托管（PENDING）
          │
          ├─ 失败(余额不足) ─▶ 请求放回 RequestBook，通知接受者
          │                     对方可再次同意 → 这次由对方付款（垫付）
          ▼
      静默期 teleport.countdown-seconds（默认 3 秒）
          │   ← 期间 flights 里仍有该 ticket
          │     /tpacancel 可在此处取消：取消待执行移动 + 全额退款
          ▼
      真正移动 → settleTeleport(ticket, moved)  → COMMITTED 或 REFUNDED
```

**三个必须记住的实现约束**（都写进了 `TeleportContext` 注释）：

1. **`flights[ticket]` 必须覆盖整个静默期。** 它是 `runCountdown` 的「仍然有效」守卫：
   `if (flights[ticket] == null) return`。
   若在预扣成功时就把它移除，倒计时会立刻自我取消，**传送永远不会发生**
   （这个 bug 真实发生过，由 `the fee is reserved on accept and the move waits for the countdown` 抓出）。
2. **`countdowns[ticket]` 要在 `refund()` 里取消。** 否则玩家在静默期退出后，
   排队中的移动仍会执行。
3. **垫付不能延长请求有效期。** `RequestBook.restore` 保留原始 `expires`，过期一律拒绝恢复，
   避免用「重试」无限续期。同时只允许**一次**垫付尝试（`awaitingSponsor` 失败后不再重置），
   否则接受者自己也没钱时会陷入无限「要不要垫付」循环。
4. **`/tpacancel` 覆盖两种状态。** 未被同意时它撤销 `RequestBook` 里的请求；已被同意、正在静默期时
   它找到 `flights` 中 `from == 自己的` 那条，调 `refund()` 同时取消待执行的移动并退回托管。
   **只有请求者能取消**（与「取消自己发出的请求」语义一致），接受者不参与。
   两条路径都走 `notifyBoth`，所以对方也会知道结果。

**为什么扣费在移动之前、结算在移动之后**：这样「钱」和「人」之间任何时刻崩溃都不会双重扣款——
预扣有 `teleport_charges` 行可恢复，启动时 `recoverPending()` 把 PENDING 退回。

`flights`、`countdowns`、`awaitingSponsor` 三个结构都由 `close()` 清理，
「先退 teleport 再排空 economy」的关闭约定不变，见 [02 §3](02-运行时与生命周期.md)。

## 5. 费用计算

`EconomyPolicy.fee`（`domain/.../EconomyPolicy.kt`）：

```kotlin
fun fee(balance: Money): Money = Money.fromMinor(
    Money.of(balance.decimal().multiply(rate).setScale(2, RoundingMode.CEILING)).minor
).coerceIn(minimum.minor, maximum.minor)
```

即：**扣费前余额 × rate → 向上取整到分 → 限制在 [minimum, maximum]**。

`rate` 是**小数比例**不是百分数：`0.001` = 0.1%。填 `1` 会被 `init` 里的
`require(rate >= 0 && rate <= 1)` 拒绝。

默认 `minimum=1.00`、`maximum=233.00`，所以**零余额传送也要扣最低 1**（coerceIn 会把 0 抬到下限）。

| 扣费前余额 | × 0.001 | CEILING 到分 | clamp 后 | 实际费用 |
|---|---|---|---|---|
| 500 | 0.500 | 0.50 | 1.00 | **1** |
| 1000.01 | 1.00001 | 1.01 | 1.01 | **1.01** |
| 12345.67 | 12.34567 | 12.35 | 12.35 | **12.35** |
| 500000 | 500.000 | 500.00 | 233.00 | **233** |

**请求时显示的是预估**（`tpa-estimate`），接受时按当时的余额重算——README 明确说明
「实际接受时余额变化可能改变费用」。

## 6. 容量预留规则（最容易漏掉的部分）

余额上限不只考虑当前余额，还要给**未完成的传送退款留出空间**。

### 6.1 钱包预留退款额度（`SqliteWalletRepository.kt:60-68`）

```kotlin
private fun pending(player: UUID) = scalar(
    "SELECT COALESCE(SUM(fee),0) FROM teleport_charges WHERE player=? AND state='PENDING'", player)

private fun write(before: Wallet, after: Money, operation: Operation): Transaction {
    // Keep refund headroom even when a deposit, payment or admin set arrives during teleport.
    if (after.minor > Money.MAX_MINOR - pending(before.player)) throw EconomyException(EconomyError.LIMIT_EXCEEDED)
    ...
}
```

**场景**：玩家余额已满，同时有一笔 PENDING 传送费。若管理员直接 `set` 到上限，
之后退款就没有空间了，钱会被卡住。这条规则让所有写操作都退一步。

**注意它影响 `claimDaily`**（见 6.3）和 `transfer` 的收款方——`write()` 是共同出口。

### 6.2 税收池上限（`:94-95`）

```kotlin
val held = scalar("SELECT COALESCE(SUM(fee),0) FROM teleport_charges WHERE state='PENDING'")
if (treasury().minor + held > Money.MAX_MINOR - fee.minor) throw EconomyException(EconomyError.LIMIT_EXCEEDED)
```

池子余额 + 所有在途暂存也不能超上限。

### 6.3 每日补助的三重 min（`:124-135`）

```kotlin
if (scalar("SELECT COUNT(*) FROM daily_claims WHERE player=? AND day=?", player, date) > 0)
    return@atomic Settlement(Money.ZERO)                                    // 今日已领

val paid = Money.fromMinor(minOf(
    amount.minor,                                        // 配置金额
    treasury().minor,                                    // 池子余额 —— 不凭空增发
    Money.MAX_MINOR - wallet.balance.minor - pending(player)   // 钱包容量（含退款预留）
))
// An empty pool does not consume today's eligibility; /eco daily can retry later.
if (paid.minor == 0L) return@atomic Settlement(Money.ZERO)  // ← 不写 daily_claims

write(...); execute("INSERT INTO daily_claims ...")         // 只有真的发出去了才记
```

**关键语义**：
- **只有发出正金额才算「今日已领取」**（`daily_claims` 只在 `paid > 0` 时插入）。
- **空池 / 补助关闭 / 钱包无容量都不消耗资格**，之后 `/meowo eco daily` 可重试。
- 领取日期用配置时区：`LocalDate.now(clock.withZone(settings.zone))`，
  默认 `Asia/Shanghai`。`Clock` 可注入以便测试（`SettlementApplicationService` 构造参数）。

## 7. 转账

`transfer`（`:75-83`）在**一个事务**里：

```kotlin
if (from == to) throw EconomyException(SELF_TRANSFER)
if (amount.minor == 0L) throw EconomyException(INVALID_AMOUNT)
val sender = getOrCreate(from); val recipient = getOrCreate(to)
val debit  = write(sender, sender.balance - amount, Operation.PAY_SENT)       // 失败 → 整体回滚
val credit = write(recipient, recipient.balance + amount, Operation.PAY_RECEIVED)  // 收款方溢出也回滚
execute("INSERT INTO transfers(...) VALUES (...)", debit.id, from, to, amount.minor)
```

- **收款方溢出会让双方一起回滚**（同一事务）。
- **转账本身不征税**（税收只来自传送）。
- 一次转账产生**两条** `transactions` 和**两条** `BalanceChanged`。
- 命令层另有正则前置拦截：`[0-9]{1,12}([.][0-9]{1,2})?`（`EconomyCommand.kt`），
  拒绝负数、`NaN`、`1e3`、三位小数、13 位整数。

## 8. 操作类型枚举

`domain/.../Wallet.kt`：

```kotlin
enum class Operation { DEPOSIT, WITHDRAW, SET, PAY_SENT, PAY_RECEIVED, TP_RESERVE, TP_REFUND, DAILY_SUBSIDY }
```

- `Wallet.change` 只处理 `DEPOSIT` / `WITHDRAW` / `SET`；
  其余（结算类）**抛异常**，必须走 `SettlementRepository` 的原子事务。这是领域层主动挡住的错误路径。
- `Operation.name` 直接进 `transactions.operation` 和 `BalanceChanged.operation`。
  **重命名枚举值会改变已存库数据和事件契约**——视为破坏性变更。
