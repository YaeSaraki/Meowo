# 18 · invsee context：窗口只是镜像，每次拿取立刻写进真实背包

`/invsee <玩家>` 让管理员打开别人的背包，看、取、交换。权限 `meowo.admin.invsee`（OP 默认，
且是 `meowo.admin` 的子节点 —— 可以只把「看背包」这一件事交给版主，不连带其它管理）。

| 动作 | 结果 |
|---|---|
| 在窗口里左键 / 右键 | 整叠取到管理员手上（左右键行为一致） |
| 在窗口里 Shift + 左键 | 直接进管理员自己的背包，不经过手上 |
| 在窗口里按 Q / 数字键 / 双击 / 中键 | **拒绝**，并说明该用哪几种键 |
| 拖拽进窗口 | **拒绝**，并提示先拿起再点 |
| 在管理员自己背包那半边普通点击 | 原版规则，完全不管 |
| 在管理员自己背包那半边 Shift + 左键 | 变成一次真实给予（满仓溢出掉在对方脚下） |

---

## 1. 唯一要记住的不变量：**真实背包是唯一真相**

```
点击 → 读目标真实 PlayerInventory → 立刻写回 → 取消事件 → 重画那一格
```

窗口是 `Bukkit#createInventory` 造出来的**镜像**，不是一个能落地的容器。
`InventoryClickEvent` 在原版动手**之前**触发，而原版不管你怎么点，改的都是那个镜像 ——
目标的 `PlayerInventory` 一下都不会动。

于是如果放任原版跑：管理员手上凭空多一份，目标包里的原件还在原地。**每点一次就复制一次。**
所以这个 context 的每一次点击都自己执行搬运，然后 `isCancelled = true`；
`InvseeClick.plan` 决定的也正是「搬哪一叠、搬到哪」，事件本身只负责执行。

同理，**写回没有「关窗时结算」这一步**。管理员被踢、context 被 `/meowo reload` 关掉、
目标中途下线，都不会有任何一叠物品停在窗口里等一条可能永远不走的退出路径 ——
东西在点下去的那一瞬间就已经在正确的人身上了。

## 2. 槽位映射：唯一来源是一张表

`PlayerInventory` 的存储和窗口是**反的**：快捷栏在 0–8、三行仓储在 9–35，而箱子式窗口
是左上到右下读的。把这两者搞混的 invsee 一眼看上去完全正常，直到管理员拿走"第四行"、
手里出现一叠快捷栏的东西。

护甲那一行反得更隐蔽：袋子里装备是**从脚往上**存的（36 靴子、37 护腿、38 胸甲、39 头盔，
对应 `EquipmentSlot` 的尾部顺序），而窗口是**从头往下**读的。所以这一行是倒着走的
（`39 - offset`）。写成 `36 + offset` 看着天衣无缝，实际是把一双靴子摆在"头盔"的位置上。

所以映射写在 `InvseeLayout` 一张表里，两个方向都从它派生，`slotOf` 不可能和 `indexOf` 不一致：

| 窗口槽位 | PlayerInventory 索引 | 内容 |
|---|---|---|
| 0–26 | 9–35 | 三行仓储 |
| 27–35 | 0–8 | 快捷栏 |
| 36–39 | **39–36** | 头盔、胸甲、护腿、靴子 |
| 40 | 40 | 副手 |
| 41–53 | — | 填充（玻璃板），背后什么都没有 |

`indexOf` 返回 `Int?` 而不是 `Int`，就是为了让"背后什么都没有"这一格必须被拒绝，
而不是被当成索引 45 写进一个不存在的格子。

## 3. 其它几条规则，以及它们各自防的是什么

- **只有左键 / 右键 / Shift 被理解**（`InvseeClick.isSupported`）。Q、数字键、双击、中键
  各自有原版自己的事务，全部落在镜像上。与其让管理员按一个没反应的键，不如告诉他该按哪个。
- **左右键故意一致**。管理员在处置别人的财产，"右键取一半"是一个还得手工撤销的拆分。
- **拖拽拒绝而不是复刻**。原版把一次拖拽摊到多个格子上有自己的规则，
  对着别人的包再实现一遍物品算术，是这个 context 唯一不能做错的事。
- **会话用 holder 认，不认标题**。标题是可本地化的，别的插件也可能用同一个（见 [16 §3.1](16-shadowbox.md)）。
- **残留会话回收，不报"已打开"**。窗口不在管理员面前 = 上次没开成或关窗事件丢了；
  一次失败不该把管理员锁到本次登录结束。
- **每次点击重新校验权限**。路由只在开窗那一刻查过；开着窗被收回的权限，
  在下一次交互时结束窗口，而不是等到下一次无害的交互。
- **目标自己动了背包，窗口跟着重画**（`watched` 反向索引）。镜像必须能自愈，
  否则管理员会对着一个过期的画面操作 —— 那才是真正的复制来源。

## 4. 生命周期

| 事件 | 做什么 |
|---|---|
| 管理员关窗 | 丢弃会话 |
| **目标**退出 / 死亡 | 关掉管理员的窗口（背包已清空，画面已经没有意义） |
| 管理员退出 | 丢弃会话 |
| context `close()` | 关掉所有窗口 |
| 开窗失败 | 立刻丢弃会话，不留一个"永远打不开"的会话把管理员锁死 |

窗口的关闭一律**排在下一 tick**（`nextTick`）：在 `InventoryClickEvent` 里改玩家的视图
会让客户端不同步（Paper 对此有明文要求，见 [16 §3.2](16-shadowbox.md)）。

## 5. 测试

- `InvseeLayoutTest` / `InvseeClickTest`：纯 JUnit，钉住槽位表与点击真值表。
- `InvseeContextTest`：MockBukkit 走真实事件，断言的是**搬运前后两个真实背包**，
  而不是原版会移动的那一叠 —— 对这个功能来说这正是正确的接缝，
  因为整个处理器的存在意义就是不让原版碰这些东西。
  核心用例是 `every transfer conserves the number of items on both sides`：
  管理员 + 目标两人身上的物品总数在来回调换之后必须一模一样。

`Messages` 在测试夹具里读不到语言包，所以 `talk`（发消息）与 `titleOf`（窗口标题）
是构造参数，默认值与其他 context 完全一致 —— 与 `FlyContext` 同一个理由。

## 6. 加一条新转移动作时

1. 在 `InvseeClick.Plan` 里加一个分支，并在 `InvseeClickTest` 里加它的那一行真值表。
2. 在 `InvseeContext.take` 里执行它 —— **先改真实背包，再取消事件**，
   顺序反了就会出现"原版搬一次、我们也搬一次"。
3. 每加一个语言键，**中英两个文件都要加**（[08 §2](08-坑与反模式.md)）：
   缺键不会报错，只会让玩家把 `invsee-xxx` 当句子读。
