# 06 · 测试与验证

## 1. 分层原则

| 层 | 依赖 | 速度 | 放哪 |
|---|---|---|---|
| 领域规则 | **纯 JUnit**，无 Bukkit | ~0.2s | `contexts/meowo-economy/domain/src/test/`、`platform/src/test/` |
| 端口/编排 | 纯 JUnit + 端口 fake | 毫秒级 | `contexts/*/src/test/`（render、shared、teleport） |
| 持久化 | **真实 SQLite**（`@TempDir`） | 亚秒 | `contexts/meowo-economy/src/test/` |
| 集成 | **MockBukkit** | 秒级 | `core/src/test/` |

`platform` 也有自己的纯 JUnit 层（`LocaleResolverTest`）。判据是
**「这段逻辑出错时会不会静默降级」**——locale 归一化错位只会让玩家看到错语言，
不抛异常，只能靠直接单测兜住，见 [08 §6c](08-坑与反模式.md)。

**领域测试绝不启动 MockBukkit。** 这是本架构最主要的收益（`plan.md` 决策表：
单模块必须启 MockBukkit ~3s，多模块 domain 纯 JUnit ~0.2s）。别破坏它。

`RenderService` 的测试用**手写 fake renderer**（`RenderServiceTest` 里的 `Renderer` 类），
不启动 Bukkit 也不发包——它只验证数量上限、失败回滚、清理。

## 2. 基础设施层测试用真 SQLite

```kotlin
class SettlementRepositoryTest {
    @TempDir lateinit var dir: Path
    @Test fun `...`() {
        SqliteWalletRepository(dir.resolve("eco.db")).use { repo -> ... }
    }
}
```

`SqliteWalletRepository` 实现 `AutoCloseable`，统一用 `.use`。

**要覆盖的场景**（现有 8 个测试已覆盖，按需扩展）：

- 重开数据库后余额仍在
- 流水写入失败 → 余额回滚
- **两连接并发更新**（`DriverManager` 直接开第二个连接）
- 转账原子性：收款方溢出会让**双方一起回滚**
- 托管 `reserve → commit → 重复完成` 只收一次税
- 失败移动退款
- 每日领取幂等

## 3. MockBukkit 夹具（`core/src/test/.../MeowoRuntimeTest.kt`）

三个非显然的点，缺一个测试就跑不起来：

```kotlin
open class TestPlugin : JavaPlugin()          // ① 必须有 open 的 JavaPlugin 子类

@BeforeEach fun setup() {
    server = MockBukkit.mock()
    // ② 显式加载本项目的 plugin.yml（路径相对 core 模块）
    plugin = MockBukkit.loadWith(TestPlugin::class.java, java.io.File("build/resources/main/plugin.yml"))
    // ③ MockBukkit 不会自动注册描述文件里的权限，必须手动补
    plugin.description.permissions.forEach { server.pluginManager.addPermission(it) }
    plugin.saveDefaultConfig()
    configure { it.set("contexts.render", false) }   // 默认关 render，避免依赖 PacketEvents
    runtime = MeowoRuntime(plugin); runtime.start()
}

@AfterEach fun teardown() {
    try { if (::runtime.isInitialized) runtime.close() } finally { MockBukkit.unmock() }
}
```

**为什么 `contexts.render` 默认关掉**：MockBukkit 环境里没有 `packetevents` 插件，
`RenderContext.start()` 的 `check(isPluginEnabled("packetevents"))` 会抛异常。
渲染逻辑另有 `RenderServiceTest` 覆盖。

**`configure` 辅助方法**改配置文件：

```kotlin
private fun configure(action: (YamlConfiguration) -> Unit) {
    val file = plugin.dataFolder.resolve("config.yml")
    val yaml = YamlConfiguration.loadConfiguration(file); action(yaml); yaml.save(file)
}
```

改完必须 `server.dispatchCommand(server.consoleSender, "meowo reload")` 才生效。

### 异步测试的两个辅助

```kotlin
private fun balance(id: UUID): BigDecimal {
    val result = api().balance(id).toCompletableFuture().get(5, TimeUnit.SECONDS)
    server.scheduler.performTicks(1)      // ← 关键：把排队的 runTask 跑掉
    return result
}
private fun flush(id: UUID) { repeat(4) { balance(id) } }   // 排空整条经济队列
```

- `get(5, SECONDS)` 等经济工作线程完成。
- **`server.scheduler.performTicks(1)` 跑掉 `host.mainThread` 排的任务**，否则断言消息时序不对。
- `flush` 调多次，因为一个业务可能产生**多条**排队任务（如
  `balance → thenCompose claimDaily → whenComplete`）。

> `flush` 里的 4 次是经验值。若新增的链路更长，改这个数——它不是契约。

**`dispatchCommand` 之后必须 `flush`（或至少 `performTicks`）才能读到消息。**
命令的结果经经济线程 → `host.mainThread` 回主线程 → 才真正发给玩家；
不 tick 的话 `nextMessage()` 返回 `null`。这是本项目测试里最常见的 NPE 来源。

### 多行消息会打破"取第一条"的假设

语言文件里的 `\n` 会被 `Messages.send` 拆成**多条**聊天消息。
所以 `pay-sent` 这类两行文案，断言完第一行后**必须清空剩余行**，否则下一条断言会读到上一条命令的尾巴：

```kotlin
assertTrue(payer.nextMessage()!!.contains("ฅ2.50 Meo"))   // pay-sent 第 1 行
assertTrue(receiver.nextMessage()!!.contains("ฅ2.50 Meo"))
drain(payer); drain(receiver)                              // ← 清掉第 2 行
server.dispatchCommand(payer,"pay Payer 1"); flush(payer.uniqueId)
assertTrue(payer.nextMessage()!!.contains("自己"))
```

`drain` 接收 MockBukkit 的 `MessageTarget`（`PlayerMock` 与 `ConsoleCommandSenderMock` 都实现了它）：

```kotlin
private fun drain(target: MessageTarget) { while (target.nextMessage() != null) { } }
```

需要跨多行断言时，直接收集再整体断言，更稳：

```kotlin
val lines = generateSequence { a.nextMessage() }.toList()
assertTrue(lines.size >= 2)
assertTrue(lines.all { it.contains("§") })
```

### 传送测试用注入的 move

`teleport` 的世界移动无法在 MockBukkit 里验证，所以 `TeleportContext` 把移动动作做成
**构造参数**（`move: (Player, Player) -> Boolean`）。测试注入计数 lambda：

```kotlin
private fun teleportHarness(
    move: (Player, Player) -> Boolean,
    particles: Boolean = false,
    action: (CommandRouter, TeleportContext) -> Unit
) {
    val bus = EventBus { _, error -> throw error }        // 订阅者错误直接抛出，便于发现
    val messages = Messages(plugin).apply { load("zh_CN") }
    val router = CommandRouter(messages)
    val context = TeleportContext(PlatformHost(plugin, bus, router, messages), TeleportSettings(5, particles), move)
    context.start()
    try { action(router, context) } finally { context.close(); bus.close() }
}
```

用 `router.onCommand(...)` 直接派发，绕开 `plugin.yml` 的命令注册。
`TeleportSettings(5, ...)` 把过期时间压到 5 秒以便测试过期。

## 5. 覆盖率门禁

`build.gradle.kts:196-234` 定义 `verifyCoverage`：

| 指标 | 门禁 | 实测 |
|---|---|---|
| 总体行覆盖率（**全部模块** main 输出聚合） | ≥ 70% | **86.96%** |
| economy domain 行覆盖率 | ≥ 90% | **94.74%**（未覆盖行都在接口声明上，非可执行逻辑） |

```
total = build/reports/jacoco/coverageReport/coverageReport.xml          （根聚合）
domain = contexts/meowo-economy/domain/build/reports/jacoco/test/jacocoTestReport.xml
```

**每模块自身覆盖率也会打印**（`build.gradle.kts:227`，只读数、不是门禁）。聚合口径会把
「别的模块的集成测试覆盖了本模块的类」也算进去，于是 `teleport` / `sit` / `home` / `shop`
四个 context 自己的 `Context` 类在本模块里是 **0 覆盖**，而总分行里看不出这个洞。
打印每个模块自己的数字，就是为了让这个洞是看得见的。

**两个陷阱**：

1. `coverageReport` 聚合所有 subproject 的 main 输出，所以**新增模块自动计入总体分母**——
   加一个没测试的模块会拉低总体覆盖率。
2. domain 那个路径是**硬编码**的（`build.gradle.kts:210`）。若新增独立 domain 模块并想单独设门禁，
   必须手动加一条 `coverage(...)` + `check(...)`，否则它只被算进总体分。

**门禁是「不许低于」，不是「每次都要涨」。** 覆盖率下降但仍过门禁时，
在 `docs/minimax/README.md` 基线表更新实测值即可。

## 6. 报告位置

```bash
# 聚合覆盖率 HTML
open build/reports/jacoco/coverageReport/html/index.html
# 各模块测试报告
open */build/reports/tests/test/index.html
open contexts/*/build/reports/tests/test/index.html
# 机器可读
cat */build/test-results/test/*.xml
```

统计全部测试数（比 `verification.json` 可靠，它是一次性快照）：

```bash
python3 - <<'PY'
import glob, re, xml.etree.ElementTree as ET
t=f=e=s=0
for p in glob.glob("**/build/test-results/test/*.xml", recursive=True):
    if re.search(r' \d+\.xml$', p): continue      # 跳过 iCloud 冲突副本，见 08 §18
    r=ET.parse(p).getroot()
    if r.tag!="testsuite": continue
    t+=int(r.get("tests",0)); f+=int(r.get("failures",0))
    e+=int(r.get("errors",0)); s+=int(r.get("skipped",0))
print(f"tests={t} failures={f} errors={e} skipped={s}")
PY
```

> ⚠️ **`skipped` 必须为 0。** `BUILD SUCCESSFUL` + `skipped>0` 等于
> 「那部分逻辑根本没被验证过」—— MockBukkit 的未实现方法会让测试方法抛异常，
> 而 JUnit 把这种情况报成 **skipped 而不是 failed**，构建照样绿。
> 详见 [08 §19](08-坑与反模式.md)。

## 7. 完整验证命令

```bash
./gradlew check build --no-daemon
```

**`check` 是唯一入口。** 三道门禁已经挂在 `check` 下面（见根 `build.gradle.kts`），所以
「记得再跑一次 `verifyArchitecture`」这种靠记性维持的做法已经没有了 —— 一道门禁如果需要
被记住，它就不算存在。CI 跑的就是这一条。

| 段 | 检查什么 |
|---|---|
| `check` | 全部 subproject 的单元 + 集成测试，外加 `verifyArchitecture`、`verifyCoverage` 两道门禁与配置门禁 |
| `build` | fat jar 打包成功（含 taboolib 引导） |

单独跑某一道门禁时（例如只想看架构规则的输出）：

```bash
./gradlew verifyArchitecture --no-daemon
./gradlew verifyCoverage --no-daemon
```

### 配置门禁：`ConfigSchemaTest`

第三道门禁在 `core/src/test/kotlin/com/meowo/core/ConfigSchemaTest.kt`，它跟着 `test` 跑，
所以同样不需要单独记住。它检查的是**配置文件与读它的代码会不会各走各的**——而这正是
`config.yml` 与 Kotlin 代码天然会做的事：写在两个地方、由两双手维护，中间没有任何东西
把它们连起来。

| 检查 | 不一致时的后果 |
|---|---|
| `contexts:` 块 == `settings.gradle.kts` 的 `contexts:meowo-*` | 某个 context 只在一处出现 → 功能永远不启动，且运行时零报错 |
| `contexts:` 块 ⊆ `MeowoRuntime` 里启用的 context | 配置文件提供了、运行时装配不启用 → 又一个「配了但不生效」 |
| 代码读的每个路径都在 `config.yml` 里 | 启动时抛 `内置 config.yml 缺少配置项 …`，整个插件起不来 |
| `config.yml` 里每个选项都有人读 | 选项有注释、随包分发、**没有任何代码读它** → 看起来能调，实际什么都不会发生 |
| 版本号只声明一次，且 `MeowoRuntime` 同步**每一份**可编辑文件 | 版本号退回「只管一个文件」→ 改了布局不用 +1 → 服主的 `ui.yml` 永远落后，日志里一个字也没有 |

最后一条是这个门禁真正的价值所在：**一份「谁都不读」的配置项，和一个写错的配置项，
在服主眼里长得一模一样**。前者在服主调了半天之后才会被发现，后者至少会在日志里留下一句。

`ConfigSyncTest` 是「版本号是全局的」这句话的行为证明：服主的 `ui.yml` 会被补到当前版本，
服主自己没做过的 `ui.yml` 插件不会替他创建。

清单全部是**推导**出来的，不是写下来的：context 从文件、Gradle 设置和运行时装配三处各自
推导，选项从代码里的读取调用和文件里的键各自推导。加一个 context 或一个配置项不需要改这个
测试文件——手写清单正是这道门禁要消灭的东西。

> `docs/ui-style.md` 的「配置文件版本」一节还记着旧规则：**版本号写在 `config.yml` 和
> `ConfigVersionMerger.CURRENT_VERSION` 两处**。那已经改了 —— 两份副本可以互相矛盾，而矛盾
> 的那一种恰好是「加了键、只改了文件」，于是插件以为每个文件都是最新的，新键从此谁也没收到，
> 且不报错。现在版本号**只在 `config.yml` 里**，测试里有一条专门盯这件事。

**先 `./gradlew clean`**，原因见 [08 §1](08-坑与反模式.md)。

验证 jar 内容：

```bash
unzip -l core/build/libs/Meowo-1.0.0.jar | grep -E 'contexts|taboolib|org/sqlite' | head
shasum -a 256 core/build/libs/Meowo-1.0.0.jar
```

验证脚本语法：

```bash
bash -n scripts/*.sh
```

## 8. 什么必须人工验收

以下**无法**用自动化证明，`docs/acceptance.md` 里也仍未勾选：

- `/meowo menu` 客户端实际显示金币图标与余额
- `/meowo render spawn 10` 客户端可见 10 个盔甲架、**其他玩家不可见**
- `clear` / 传送 / 复活 / 模块停用后客户端无残留
- 与其他假实体插件并用的 ID 冲突
- Prism Launcher 自动直连

**禁止用服务端 `list` 验证实体数**——它统计的是玩家，不是实体。

PacketEvents 模块被真实加载 ≠ 客户端渲染正确。`RenderServiceTest` 验证的是
数量上限、失败回滚、清理这些**应用逻辑**，不验证网络包编码和客户端可见性。

## 9. 改测试的注意事项

- MockBukkit 4.116.1 声明 Paper build 111，本项目测试依赖是 build 129。
  **测试通过即证明兼容**；若 MockBukkit 升级导致失败，不要降级 Paper 依赖去迁就。
- 报告中 `java.base@25.0.x` 警告（Unsafe / native-access）来自 SQLiteJDBC，**不影响结果**。
- 若覆盖率因新增代码下降，先问「这段逻辑能不能用纯 JUnit 测」。
  能提到 domain 层的逻辑，测试会又快又稳——这是架构在起作用，不是欠测试。
